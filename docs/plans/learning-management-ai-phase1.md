# Laixue 学习管理与 AI 教学闭环：第一阶段总计划

> 版本：v0.1  
> 启动日期：2026-08-10  
> 规划与验收：Codex  
> 代码实现：WorkBuddy  
> 状态：已启动，当前处于 Gate 0 技术盘点

## 1. 阶段目标

第一阶段只交付一条可真实使用、可验证的教学闭环：

1. 老师基于已有 OpenMAIC 课程创建学习任务；
2. 老师指定应学人员并生成任务专属链接；
3. PC 与移动端统一采集章节进度、有效时长、AI 提问和可获取的检查题结果；
4. 管理端展示未开始、学习中、已完成、逾期及明细；
5. AI 基于确定性统计生成个人学习小结和班级教学简报；
6. AI 提出补学建议，老师确认后创建独立补学任务。

阶段验收场景：老师把一门课程发布给 30 人，能够识别未开始人员和困难章节，查看有证据的 AI 简报，并从建议创建补学任务。

## 2. 明确边界

### 本阶段必须完成

- 学习任务与任务专属链接；
- 应学人员名单；
- PC/移动端服务端进度；
- 章节完成、有效学习时长；
- 未开始、学习中、已完成、逾期；
- 任务概览、学员明细、章节分析；
- AI 个人小结、班级简报；
- AI 补学建议与老师确认创建补学任务；
- 老师数据隔离、管理员全局查看；
- 事件幂等、指标可追溯。

### 有可靠数据才展示

- AI 提问正文及主题聚合；
- 检查题已答/未答；
- 检查题正确率；
- 使用提示次数。

不得用推断值冒充事实；取得不到可靠答案时，首版只展示可验证的次数或不展示。

### 本阶段不做

- 完全自适应学习路径；
- AI 自动修改原课程；
- 自动外发微信、邮件或短信；
- 复杂组织树、证书、学分和正式考试；
- 无老师确认的自动补学或自动干预；
- 将“看完”包装成“掌握”。

## 3. 产品信息架构

### 老师/管理员端

- `/admin/dashboard`：任务与学习概览、最近 AI 简报；
- `/admin/tasks`：学习任务列表；
- `/admin/tasks/new`：选择课程、任务信息、应学人员、发布；
- `/admin/tasks/[id]`：概览、学员明细、章节分析、AI 简报；
- `/admin/students/[id]`：轻量学习档案；
- `/admin/courses`：保留课程资产管理，增加“发布学习任务”。

### 学员端

- `/learn/[token]`：任务鉴权入口；
- “我的学习任务”：只展示明确分配的任务；
- “课程广场”：自由浏览，与正式任务统计分开；
- PC 与移动端共享服务端进度事实源。

## 4. 核心口径

- **未开始**：在任务名单中，没有 `learning_started`；
- **学习中**：已经开始，尚未满足完成规则且未逾期；
- **已完成**：满足任务发布时冻结的完成规则；
- **逾期**：超过截止时间且未完成；
- **进度**：已完成必学章节数 / 发布时冻结的必学章节总数；
- **有效时长**：仅累计页面可见且近期有操作或音频播放的心跳区间；
- **开始率**：（学习中 + 已完成 + 逾期但已开始）/ 应学人数；
- **完成率**：已完成人数 / 应学人数。

到达最后一页不等于完成。AI 总结不得修改上述确定性指标。

## 5. 目标数据模型

最终命名可在 Gate 0 后冻结，但语义必须保留：

- `learning_tasks`：一次课程发布；
- `task_learners`：任务与应学人员、聚合进度；
- `learning_sessions`：一次有效学习会话；
- `learning_events`：规范化学习事件；
- `ai_learning_summaries`：个人/班级 AI 总结及数据版本；
- `ai_intervention_suggestions`：有证据的补学建议及老师处置记录。

现有 `course_assignments`、`course_progress_events`、`runtime_sessions`、`runtime_records` 的保留、扩展或迁移策略由 Gate 0 证据决定。

任务发布时必须冻结课程结构快照，至少包含课程版本、章节 ID、顺序、必学标记和可识别的检查题 ID，防止后续编辑改变历史任务口径。

## 6. 标准事件

首版事件集合：

- `task_opened`
- `learning_started`
- `scene_started`
- `scene_completed`
- `heartbeat`
- `learning_paused`
- `learning_resumed`
- `question_asked`
- `check_answered`
- `course_completed`
- `task_completed`

每个事件必须由服务端从登录态解析学员身份，客户端不得提交可信 `studentId`。事件必须有唯一 `event_id`，支持批量上传与幂等重试。

## 7. AI 输出约束

AI 输入先由程序生成统计快照，模型只负责归纳、解释和建议。

个人小结至少包含：概况、优势、待加强项、证据、下一步建议、置信度。班级简报至少包含：总体进展、关注人员、困难章节、高频问题、教学建议、补学建议。

所有建议必须：

- 指向具体任务、学员或章节；
- 至少包含一条可查看证据；
- 保存模型、提示词版本和统计数据版本；
- 数据不足时明确标记“证据不足”；
- 经老师确认后才可创建补学任务。

## 8. 交付门禁与计划

### Gate 0：技术盘点与口径冻结

- 盘点 PC/移动端所有学习入口；
- 抽样检查 `runtime_records.payload`；
- 确认提问和检查题可获取字段；
- 确认课程章节/题目快照能力；
- 输出复用/适配/补埋点决策；
- 冻结数据模型、事件字典和完成口径。

未通过 Gate 0，不开始大规模数据库和播放器改造。

### Gate 1：任务与权限闭环

- 学习任务 CRUD、应学名单、任务链接；
- 学员任务列表；
- 老师/管理员权限隔离；
- 任务发布快照。

### Gate 2：可信进度闭环

- PC/移动端统一会话与事件；
- 服务端进度、有效时长、幂等；
- 跨设备恢复；
- 修复“到最后一页即完成”。

### Gate 3：管理报表

- 任务概览、学员明细、章节分析；
- 筛选、搜索、导出；
- 提问/检查题按 Gate 0 结论接入。

### Gate 4：AI 总结

- 统计快照；
- 个人小结和班级简报；
- 证据、缓存、失败重试和版本记录。

### Gate 5：补学闭环与试点

- AI 干预建议；
- 接受、忽略、审计；
- 创建关联原任务的补学任务；
- 真实课程小范围试点。

## 9. 协作流程

每个 Gate 独立下发任务卡。WorkBuddy 必须提交：

1. 实施报告；
2. 变更文件清单；
3. 数据库迁移及回滚说明；
4. 自动化测试输出；
5. 手工验证证据；
6. 已知限制与未完成项。

Codex 对照任务卡复核代码、测试和产品口径。未通过验收不得进入下一个 Gate；发现范围变化时先修订本计划，不在代码中暗自改变产品语义。
