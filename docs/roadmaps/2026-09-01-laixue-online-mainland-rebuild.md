# laixue.online 大陆版重构任务规划卡

> 状态：待启动  
> 制定日期：2026-09-01  
> 目标环境：腾讯云北京轻量应用服务器  
> 正式域名：`laixue.online`（域名已备案，网站备案受理中）  
> 路线：保留现有产品代码，重建后端基础设施；不迁移旧用户、课程及学习数据

## 1. 一句话目标

在不依赖 Supabase、Vercel 和其他非必要境外运行链路的前提下，让 laixue 的管理员、教师、学员、课程、学习任务、学习数据和课程资产在北京服务器上形成可上线、可备份、可恢复的完整闭环。

## 2. 已确认决策

| 事项 | 决策 |
|---|---|
| 产品代码 | 保留当前 RJ-laixue fork，不从零重写 |
| 旧业务数据 | 不迁移；新环境初始化为空库 |
| 旧用户密码 | 不迁移；新环境重新创建账号 |
| 正式域名 | 使用 `laixue.online` |
| 应用部署 | 腾讯云北京轻量应用服务器，Docker Compose |
| 数据库 | PostgreSQL；首期允许与应用同机，禁止暴露公网端口 |
| 认证候选 | Better Auth + PostgreSQL，须先通过 P0 验证后锁定 |
| 对象存储 | 腾讯云 COS 私有桶，须先通过预签名上传/读取验证 |
| 权限 | 服务端应用层授权为主；不照搬 Supabase RLS |
| 发布方式 | 新环境全新上线，不做新旧系统双写 |
| 旧环境 | 上线稳定观察后再释放，默认保留 2～4 周 |

## 3. 不在本期范围

- 迁移 Supabase 用户、密码、课程、学习记录或 Storage 文件。
- 自托管整套 Supabase。
- Kubernetes、微服务、Redis、消息队列、数据库读写分离。
- 多租户、复杂组织树、通用 RBAC 权限配置器。
- COS CDN 加速；先用真实网络测试决定是否需要。
- 为旧 `laixue.work` 数据或 URL 建长期兼容层。

## 4. 复核后的关键事实

1. 当前系统不是简单的“OpenMAIC + Supabase 登录”。至少 69 个应用或服务端文件直接引用 Supabase 认证/客户端，业务还依赖 RPC、RLS、Storage、后台配音任务和文档解析链路。
2. 仓库已有原生 `pg` 依赖、PostgreSQL 契约测试和部分存储抽象，可以复用领域规则和测试，但生产路径仍主要通过 Supabase/PostgREST RPC，不能视为已经完成普通 PostgreSQL 适配。
3. 当前 Docker Compose 仅运行应用容器；数据库、反向代理、备份、健康检查均需补齐。
4. `data/classrooms`、课堂媒体、用量 JSONL 和异步生成任务仍有本机文件依赖。必须逐项决定进入 PostgreSQL、COS 还是持久卷，不能只改课程音频。
5. 当前部分长任务依赖 Next.js `after()`、轮询接口或 cron 路由。迁到常驻服务器后仍需验证重启恢复、重复执行和任务租约，避免“HTTP 请求结束后任务丢失”。
6. 移除 Supabase RLS 后，课程、任务和管理接口改用统一服务端权限判断，并覆盖核心角色边界。

## 5. 目标架构

```text
员工浏览器
    │
    ▼
laixue.online / HTTPS
    │
    ▼
Caddy 或 Nginx
    │
    ▼
Next.js 应用
    ├── Better Auth（待 P0 锁定）
    ├── PostgreSQL
    ├── 腾讯云 COS 私有桶
    ├── 后台任务执行入口
    └── 国产 LLM / TTS / ASR / 搜索 API

PostgreSQL 定时逻辑备份 ──► COS 备份桶
应用版本/系统变更前 ─────► 轻量服务器快照
```

浏览器正式运行时只允许依赖：`laixue.online`、经批准的 COS 访问域名，以及确有必要的境内第三方服务。不得再请求 `*.supabase.co`。

## 6. 分阶段任务

### P0：技术验证与范围冻结

目标：用最小代码证明选型可行，未通过不得进入大规模替换。

- [x] 建立 Supabase 使用清单，按认证、数据库、RPC、Storage、后台任务、文档解析分类。详见 `p0-a-supabase-coupling-audit.md`。
- [x] 建立现有业务表、函数、触发器、RLS 策略清单；只提炼仍需要的业务规则。新版逻辑模型见 `p0-a-postgresql-v1-schema.md`。
- [x] 用本地 PostgreSQL 验证连接池、事务、JSONB、UUID 和并发更新。
- [x] 验证 Better Auth：普通 PostgreSQL、邮箱密码登录、session、管理员创建用户、设置密码、禁用/恢复账号、注销其他 session。结果见 `p0-b-better-auth-verification.md`。
- [x] 验证 Better Auth schema 可生成 migration；正式 SQL 在 P1 纳入仓库，生产环境禁止应用启动时自动改表。
- [x] 验证 COS：私有桶、预签名上传、预签名读取、音频 Range 请求、删除对象。
- [x] 验证 COS 的虚拟主机式 endpoint 和实际北京地域配置；使用腾讯云 Node SDK。
- [ ] 在 COS 控制台配置 CORS 后，用浏览器完成真实上传、中文文件名和音频播放验证。
- [ ] 盘点所有 `fs` 写入，形成“PostgreSQL / COS / 持久卷 / 可丢弃临时文件”归宿表。
- [ ] 验证后台配音和课堂生成任务在容器重启后可识别并恢复或安全失败。
- [ ] 记录北京服务器 CPU、内存、磁盘、系统架构和带宽，完成容量判断。

P0 通过标准：

- 登录原型、数据库读写、COS 音频播放均在本地或受限测试环境通过。
- 技术栈中不存在需要继续依赖 Supabase 才能实现的核心能力。
- 若 Better Auth 的管理员账号生命周期不满足业务，暂停并重新比较 Auth.js 或自建轻量认证，不进入全面替换。
- 若 COS 预签名和音频 Range 不通过，优先采用腾讯云原生 COS SDK，不强行沿用 AWS S3 SDK。

- [x] P1-A：建立版本化 SQL migration 机制和真实空库校验测试。
- [x] P1-A：建立共享 PostgreSQL Pool并设置连接上限；进程关闭接入随部署入口完成。
- [x] P1-B：建立课程、课程资产和发布快照表，以及最小课程 repository。
- [x] P1-C～E：建立学习任务、任务名单、学习活动、聚合进度、后台任务和用量表。
- [x] 明确核心外键、唯一约束、幂等键、时间字段和删除策略。
- [x] 建立首批课程、任务、学习活动和后台任务 repository；页面切换随垂直切片进行。
- [x] 建立数据库 actor 与课程/任务核心授权边界；Better Auth session 的 `requireUser` 接线在 P2 完成。
- [x] 将现有 RuntimeStore PostgreSQL 契约适配到普通 PostgreSQL 执行层，保留版本和幂等语义。
- [x] 为课程保存、学习事件、任务发布和后台任务领取建立核心事务验证。

P1 通过标准：全新空库可通过一条受控命令初始化；migration 可重复验证；数据库不需要 Supabase schema、PostgREST 或 `service_role`。

### P2：认证与人员管理垂直切片

目标：先完成一个可独立使用的管理员—教师—学员闭环。

- [x] 接入认证 API、客户端 hook 和服务端 session。
- [x] 建立首次管理员初始化命令；只允许在尚无管理员时执行。
- [x] 改造登录、退出、共享 API guard 和登录后跳转。
- [x] 建立管理员创建教师/学员、禁用/启用、设置临时密码接口。
- [x] 采用管理员发放临时密码、用户首次登录修改的流程。
- [x] 账号禁用时撤销现有 session（P0-B 已实测）。
- [x] 保持无公开自助注册入口。
- [x] 建立三角色核心数据库权限边界和认证生命周期验证。

P2 通过标准：不配置任何 Supabase 公钥或 service role，三类账号可以完成各自登录与受限页面访问。

### P3：课程与 COS 资产垂直切片

目标：教师能生成、保存、编辑、发布和播放一门完整课程。

- [ ] 改造课程列表、详情、保存、删除、所有权和发布状态。

- [ ] 改造课程图片、音频、附件、解析产物和重新配音资产上传。
- [ ] 确认 Markdown/HTML/JSON 中嵌入资源的归一化和播放策略。
- [ ] 改造 PDF/文档解析链路；第三方解析服务需要公网 URL 时使用短期、最小权限读取 URL。
- [ ] 将可持久业务资产移出本机文件系统；临时文件使用独立临时目录并有清理策略。
- [ ] 课程删除采用数据库状态与对象清理任务解耦，支持失败重试。
- [ ] 验证大课程 JSON、批量音频、断点失败重试和浏览器 Range 播放。

P3 通过标准：新建课程全链路成功；服务器重启后课程及资产仍可用；浏览器网络请求中无 Supabase 域名。

### P4：学习任务与教学数据垂直切片

目标：学员完成真实学习，教师看到可信数据。

- [ ] 改造学习任务创建、课程包、学员分配、发布、关闭和归档。

- [ ] 事件写入使用幂等键；用户身份由当前登录会话确定。
- [ ] 明确定义“已开始、进度、有效时长、完成、得分”的唯一业务口径。
- [ ] 建立聚合快照，教学看板与 AI 数据分析默认读取聚合结果。

P4 通过标准：测试学员完成任务后，管理员和教师看到一致的进度、时长、得分和完成状态；重复上报不会重复计数。

### P5：后台任务、部署与可恢复性

目标：系统不只“能跑”，还能够在单机故障和版本发布后恢复。

- [ ] 完成生产 Docker Compose：应用、PostgreSQL、反向代理、持久卷、健康检查和日志限制。
- [ ] 数据库与内部管理端口只绑定 Docker 内网或本机回环地址。
- [ ] GitHub 构建并发布不可变镜像；生产服务器只拉取和启动，不在生产机执行完整 Next.js 构建。
- [ ] 建立后台任务 runner 或受控 cron；任务表包含租约、重试次数、下次执行时间和最终失败状态。
- [ ] 设置每日 PostgreSQL 逻辑备份并加密上传 COS；数据库备份桶与业务资产桶分离。
- [ ] 制定备份保留周期、校验、恢复命令和月度恢复演练。
- [ ] 在重大系统变更前创建轻量服务器快照；快照不能代替数据库逻辑备份。
- [ ] 配置 HTTPS、安全响应头、上传大小、请求超时、日志脱敏、磁盘/内存/证书告警。
- [ ] 增加 `/api/health` 的应用、数据库和对象存储分层检查，外部健康接口不得暴露敏感详情。
- [ ] 编写部署、回滚、恢复、密钥轮换和首次管理员初始化操作手册。

P5 通过标准：在测试环境演练一次应用回滚、一次空库恢复和一次后台任务中断恢复，并记录结果。

## 7. 统一验收清单

### 功能

- [ ] 管理员可管理教师与学员。
- [ ] 教师只能管理授权范围内的课程和任务。
- [ ] 学员只能访问分配给自己的内容。
- [ ] 课程生成、保存、编辑、发布、播放、重新配音完整可用。
- [ ] 学习任务、进度、有效时长、答题与完成数据一致。
- [ ] 教学看板、报告和 AI 分析可用。

### 去 Supabase

- [ ] 生产依赖中移除 `@supabase/ssr` 和 `@supabase/supabase-js`。
- [ ] 源码中无生产路径引用 `lib/supabase/*`。
- [ ] 生产环境不需要任何 `SUPABASE_*` 变量。
- [ ] 浏览器和服务器运行日志中无 `supabase.co` 请求。
- [ ] Supabase SQL 文件保留为历史资料，但不参与新环境初始化。

### 安全与可靠性

- [ ] 未登录、角色边界、课程归属和资产归属测试通过。
- [ ] COS 为私有桶，长期密钥不进入浏览器。
- [ ] 数据库无公网监听。
- [ ] 密码、session、API key 和签名 URL 不进入日志。
- [ ] 备份可以在空环境恢复。
- [ ] 容器重启不会丢失课程、学习数据或已入队后台任务。

### 大陆访问

- [ ] 福州目标网络均能完成登录、建课、上传、播放和学习事件上报。
- [ ] 核心首屏和登录不依赖境外字体、脚本、认证或存储。
- [ ] 外部模型或解析服务不可用时有超时、错误提示和重试边界，不拖死应用。

## 8. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 逐文件替换 Supabase 导致权限遗漏 | 严重 | 先建统一身份、repository 和授权层，再迁垂直切片 |
| 普通 PostgreSQL 无 PostgREST RPC | 高 | 把必要函数改为事务 SQL/服务方法；保留并发契约测试 |
| Better Auth 管理员生命周期不适配 | 中 | P0 验证创建、禁用、重置、撤销 session；不过门不锁定 |
| COS S3 兼容差异 | 中 | 先验证预签名、Range 和虚拟主机 endpoint；必要时使用腾讯 SDK |
| 本机文件在重启或换机时丢失 | 高 | 逐项归宿盘点；业务资产进 COS，数据库进持久卷，临时文件可清理 |
| `after()` 长任务在进程退出时中断 | 高 | 持久任务表 + 租约 + 独立 runner/cron + 幂等重试 |
| 同机 PostgreSQL 单点故障 | 高 | 每日异机逻辑备份、恢复演练、重大变更前快照 |
| 2 核 4G 构建或解析资源不足 | 中 | CI 构建镜像；实测内存峰值，必要时升 4 核 8G |
| 备案进度延迟 | 中 | 与代码重构并行；备案前只做受限测试，不提前正式开放 |
| 国产模型并非所有能力都等价 | 中 | 分别验证 LLM、图片、TTS、ASR、文档解析；按能力配置降级 |

## 9. 建议执行批次

| 批次 | 内容 | 粗略时间 | 是否可上线 |
|---|---|---:|---|
| A | P0 技术验证与范围冻结 | 2～4 天 | 否 |
| B | P1 数据地基 + P2 认证人员 | 5～8 天 | 仅内部验证 |
| C | P3 课程与资产 | 5～8 天 | 教师灰度 |
| D | P4 学习任务与教学数据 | 5～8 天 | 小范围业务灰度 |

整体预估为 3～5 周的专注开发与验证时间。旧数据不迁移已经显著缩短范围，但 69 个直接耦合文件、数据库 RPC、后台任务和资产链路决定了它仍不是“一周换几个环境变量”的工作。

## 10. 启动条件与完成定义

启动条件：

- 北京轻量服务器配置已记录，SSH 和安全组由负责人可控。

- `laixue.online` 网站备案可继续与开发并行推进。
- 明确首期账号发放方式采用管理员创建，不开放公众注册。

项目完成定义：
