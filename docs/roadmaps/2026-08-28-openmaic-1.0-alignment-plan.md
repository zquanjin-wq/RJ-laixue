# RJ-laixue 对齐 OpenMAIC 1.0 路线图

> 状态：规划完成，暂不启动实施  
> 制定日期：2026-08-28  
> 启动条件：现有在制任务全部完成、合入、验证，并形成干净可追溯的 Git 基线  
> 核心策略：产品范式对齐、上游能力选择性移植、RJ 企业学习能力保持独立演进

---

## 1. 背景与目标

OpenMAIC 1.0 的主要变化不是单纯增加功能，而是把产品从“一次生成一节互动课堂”推进为“以对话为中心的课程生产工作台”，包括：

- 三栏式 Pro Workbench；
- 对课程、场景和具体元素的精确引用；
- 幻灯片、测验、交互页面和 PBL 的全组件 AI 编辑；
- 从单课生成升级到课程级规划和连续课时生成；
- PPTX 高保真导入、音视频转课；
- 深度研究、风格复用、教学风格迁移和自定义 Skill。

RJ-laixue 已具备编辑器、AI 编辑工具、PBL v2、云端课程、账号权限、学习任务、教学数据和移动端学习等基础。本路线图的目标不是复制 OpenMAIC 1.0，而是形成：

> AI 课程生产工作台 + 企业学习运营闭环

### 1.1 对齐目标

1. 让教师能通过自然语言精确修改课程中的任意对象。
2. 让 AI 能规划和生成多节连续课程，而不只是一组 scenes。
3. 把生成策略、视觉风格和教学方法沉淀为可治理、可复用的 Skill。
4. 保持课程生成、发布、学习、数据分析的端到端闭环。
5. 持续吸收 OpenMAIC 开源主线的基础设施、安全与兼容性改进。

### 1.2 非目标

- 不直接全量 merge OpenMAIC 1.0 或 Pro 版本代码。
- 不为了视觉相似而重写现有编辑器。
- 不在第一阶段建设开放 Skill 市场。
- 不用一个无限权限的“修改整个课程 JSON”工具替代受控编辑工具。
- 不在当前其他任务仍未收口时并行启动大范围架构改造。

## 2. 总体原则

### 2.1 双线对齐

| 路线 | 内容 | 方式 |
|---|---|---|
| 上游基础设施线 | DocumentStore、RuntimeStore、资产注册、安全修复、生成 SDK、导入导出 | 按 commit 链评估后定向移植 |
| RJ 产品能力线 | 精确引用、全组件编辑、课程规划、Skill、企业发布运营 | 在 RJ 业务模型上自主实现 |

### 2.2 兼容优先

- 上游 DSL 不直接承载 RJ 的账号、学习任务和企业运营字段。
- RJ 扩展字段继续通过 registry、serialize 和金丝雀测试保护。
- 每次上游同步先验证数据兼容，再接 UI。
- 云端 Supabase 与私有化 Postgres 保持同一业务契约、不同部署 adapter。

### 2.3 渐进交付

- 每个阶段必须可独立上线或由 feature flag 关闭。
- 新旧路径并存期间，旧路径仍是可用回退方案。
- 先建设契约和观察能力，再扩大 AI 写权限。
- 每个阶段只解决一个主要产品问题，避免工作台、数据层、Skill 同时大改。

## 4. Phase 1：基础设施与上游兼容基线

### 4.1 目标

补齐支撑后续课程级生成和 Skill 的数据地基，避免新能力继续依赖只适合单机课堂的存储路径。

### 4.2 工作范围

1. 重新审计 OpenMAIC v0.3.1、v0.3.2 及 1.0 公开部分的变更。
2. 完成 DocumentStore/RuntimeStore 的既定迁移路线。
3. 评估并引入资产注册中心和增量保存能力。
4. 精准回捞 SSRF、导入解析和编辑器稳定性修复。
5. 建立部署期可替换的 RuntimeStore adapter：
   - 云端：Supabase/Postgres + RLS；
   - 私有化：自托管 Postgres + 企业认证；
   - 浏览器不直接使用 service role 写入。
6. 明确 `learnerKey = auth.uid()`，匿名访问码不获得运行时写分区。

### 4.3 明确不做

- 不在本阶段调整工作台主要 UI。
- 不建设 Skill 管理页面。
- 不引入课程级规划数据模型。

### 4.4 验收标准

- 旧课程可读取、编辑、保存、播放，不丢 RJ 扩展字段。
- 新旧存储切换可由 feature flag 控制。
- 并发追加记录具备明确的冲突处理或 CAS 语义。
- 云端与私有化实现通过同一套 contract tests。
- 资产 URL 不出现新增 base64 持久化。
- 关键 API 的 owner/role 校验通过安全测试。

预计工期：2–3 周。

## 5. Phase 2：精确引用式 AI 编辑

### 5.1 目标

把已有的当前场景、选中元素和 AI 编辑能力统一成显式引用体系，使编辑结果稳定落到用户指定对象。

### 5.2 核心数据模型

新增统一引用结构 `CourseReference`：

```ts
type CourseReference =
  | { type: 'course'; courseId: string }
  | { type: 'scene'; courseId: string; sceneId: string }
  | { type: 'element'; courseId: string; sceneId: string; elementId: string }
  | { type: 'quizQuestion'; courseId: string; sceneId: string; questionId: string }
  | { type: 'pblTask'; courseId: string; sceneId: string; taskId: string }
  | { type: 'agent'; courseId: string; agentId: string };
```

引用必须包含稳定 ID，不以标题、数组下标或当前页面状态作为唯一定位依据。

### 5.3 用户体验

- 左侧课程/场景菜单提供“引用到 AI”。
- 画布选择元素后出现“用 AI 编辑”。
- Quiz 问题、PBL 任务和课堂智能体支持对象级引用。
- 输入框支持 `@` 选择器和引用 chips。
- AI 消息展示本次读取和修改的对象范围。
- 写操作前显示变更摘要；高影响操作支持确认或预览。
- 编辑后可撤销，并能定位到实际发生变化的对象。

### 5.4 工具层改造

- 所有编辑工具接收显式 reference，而不是只依赖 active scene。
- read 工具输出最小必要上下文。
- mutation 工具继续使用 schema 校验、JSON Patch 白名单和操作级权限。
- 引用对象不存在或版本过期时拒绝写入并提示重新选择。
- 为每次 AI 修改记录 trace：发起人、目标对象、工具、补丁和结果。

### 5.5 验收标准

- 用户可以引用整课、scene、slide element、quiz question 和 PBL task。
- 同一对话中引用多个对象时不会误改当前页面。
- 对象被删除或重排后不会因数组下标变化误写。
- AI 修改具备预览、撤销、历史记录。
- 固定编辑用例成功率达到 90% 以上，误修改非目标对象为 0。

预计工期：2–3 周。

## 6. Phase 3：全组件 AI 编辑

### 6.1 目标

让 Slide、Quiz、Interactive、PBL 和课程结构都具备受控 AI 编辑能力。

### 6.2 分批顺序

#### 3A. Slide 加固

- 元素文本、样式、位置、层级和图片替换；
- 整页重生成与局部编辑边界明确；
- 动作、旁白与元素 ID 联动校验；
- 并发编辑冲突提示。

#### 3B. Quiz

新增受控工具：

- 读取题目；
- 新增/删除/重排题目；
- 修改题干、选项、答案和解析；
- 调整题型、难度和知识点；
- 校验答案合法性与评分规则。

#### 3C. Interactive

- 在现有 HTML str-replace 基础上补 schema/DOM 级约束；
- 编辑后执行安全检查和 iframe 预览；
- 验证交互控件、响应式布局和教师动作目标仍有效；
- 保留完整替换作为失败回退，不作为默认路径。

#### 3D. PBL

- 编辑背景、角色、目标、里程碑、交付物和评价规则；
- 防止运行中的学习项目被静默改变；
- 已发布 PBL 修改产生新版本，不覆盖学员历史快照。

#### 3E. 课程结构

- 插入、删除、复制和重排场景；
- 批量统一语气、难度和视觉风格；
- 批量生成旁白或替换教师声音；
- 高影响批量操作必须预览和确认。

### 6.3 验收标准

- 五类对象都具备 read → plan → validate → apply → verify 链路。
- AI 写工具不能绕过 owner/role、schema 和发布版本规则。
- 已发布课程的学习记录不会因编辑而错位。
- 失败操作不留下半写入状态。
- 每类编辑建立不少于 20 个固定评测用例。

预计工期：3–4 周。

## 7. Phase 4：课程级规划与连续课时生成

### 7.1 目标

从“生成一门课堂”升级为“规划、生成、发布一组有学习递进关系的课程”。

### 7.2 建议模型

```text
CourseProgram
├─ title / description
├─ audience / prerequisites
├─ learningGoals
├─ estimatedDuration
├─ styleProfileId
├─ teachingSkillIds[]
├─ sourceMaterialIds[]
└─ lessons[]
   ├─ lessonId
   ├─ sequence
   ├─ objectives
   ├─ prerequisiteLessonIds[]
   ├─ assessmentPlan
   └─ classroomId / generationStatus
```

`CourseProgram` 是课程计划；现有 Stage/Classroom 仍是单节可播放课程。两者不要合并为一个超大 JSON。

### 7.3 生成流程

1. 教师输入主题、对象、总课时、单课时长、材料和教学要求。
2. AI 生成课程地图、学习目标与考核安排。
3. 教师编辑并锁定课程地图。
4. 系统按节异步生成，每节有独立状态和重试。
5. 课程级校验器检查：
   - 知识递进；
   - 重复内容；
   - 前置依赖；
   - 难度曲线；
   - 测验覆盖；
   - 总时长。
6. 教师进行跨课批量修改。
7. 发布为现有学习任务或课程包。

### 7.4 失败与恢复

- 课程计划和每节生成任务分开持久化。
- 单节失败不回滚已完成课时。
- 支持从失败课时继续、重新生成或跳过。
- 锁定后的课时不会因其他课时重试而自动变化。
- 发布后修改使用版本化课程包。

### 7.5 验收标准

- 支持 3–20 节课程规划和异步生成。
- 生成中可暂停、重试和继续。
- 任一失败不导致整套课程丢失。
- 课程可直接进入现有学习任务发布流程。
- 报表能按课程计划、课时和学员三个层级聚合。

预计工期：3–4 周。

## 8. Phase 5：RJ Skill 系统

### 8.1 目标

把散落在代码和提示词中的生成经验沉淀为可版本化、可授权、可评测的教学能力包。

### 8.2 Skill 分类

| 类型 | 作用 | 第一批示例 |
|---|---|---|
| ContentSkill | 决定内容研究和组织方法 | 深度研究、职业任务、案例课 |
| StyleSkill | 决定视觉系统 | 锐捷品牌、PPT 模板复用、简洁图解 |
| TeachingSkill | 决定教学行为 | 工作坊、苏格拉底提问、讲练结合、PBL |

### 8.3 Manifest 建议

```text
id / name / version / type
description
owner / visibility
inputSchema
promptFragments
generationPolicy
supportedSceneTypes
requiredCapabilities
evaluationSuite
createdAt / updatedAt
```

### 8.4 运行规则

- Skill 只能声明允许的生成策略，不直接获得任意代码执行能力。
- 多 Skill 组合需要明确优先级和冲突规则。
- 每门课记录实际使用的 Skill ID 和版本。
- Skill 更新不自动改变已发布课程。
- 官方 Skill 上线前必须通过固定评测集。
- 企业私有 Skill 只能被授权组织和教师使用。

### 8.5 第一批 Skill

1. 深度研究课程。
2. 企业内训标准课。
3. 锐捷品牌视觉风格。
4. PPT 模板风格复用。
5. 工作坊课程。
6. PBL 项目式课程。

### 8.6 暂缓能力

- 公共 Skill 市场；
- 未审核第三方代码型 Skill；
- 自动从任意教学视频生成并立即发布 Skill；
- Skill 付费、评分和社区分发。

### 8.7 验收标准

- Skill 可创建、版本化、启停和授权。
- 课程生成结果可追溯到具体 Skill 版本。
- 同一输入使用同一 Skill 时关键结构具备稳定性。
- Skill 冲突有确定性解析规则。
- 禁用 Skill 不影响历史课程播放。

预计工期：3–4 周。

## 9. Phase 6：材料转课与教学风格迁移

### 9.1 PPT 风格复用

1. 导入 PPTX。
2. 提取主题色、字体、标题层级、留白、常用版式和图表样式。
3. 生成可人工调整的 Style Profile。
4. 保存为 StyleSkill。
5. 生成新课程并做版式溢出、字体和品牌一致性检查。

### 9.2 音视频转课

1. 上传音频/视频。
2. 异步抽取音轨、转写、章节切分和关键帧。
3. 教师确认课程大纲。
4. 生成 Slide/Quiz/Interactive/PBL。
5. 保留时间戳引用，便于回看来源。

### 9.3 教学风格迁移

第一版只提取可解释特征：

- 讲解节奏；
- 提问频率；
- 案例密度；
- 互动方式；
- 语气和受众难度；
- 每段讲授与练习的比例。

风格画像必须由教师确认后才能保存为 TeachingSkill，不直接复制教师肖像、声音或受版权限制的内容。声音克隆继续走单独授权流程。

### 9.4 验收标准

- PPT 风格复用在固定模板集上达到可接受的一致性。
- 音视频材料处理支持断点续作和失败重试。
- 生成课程能追溯到原始材料章节/时间戳。
- 风格迁移结果可人工查看、编辑和拒绝。

预计工期：3–4 周。

## 10. 企业运营能力的联动要求

所有新能力必须接入 RJ 现有业务闭环：

### 10.1 权限

- 管理员：组织级 Skill、模板和课程计划治理。
- 教师：创建、编辑、发布本人有权限的课程。
- 学员：只消费已发布版本并写入本人学习记录。
- AI 工具权限不高于当前登录用户权限。

### 10.2 发布

- 草稿、审核、已发布、已归档状态清晰。
- 发布内容形成不可变版本快照。
- 修改已发布课程时创建新版本，并定义进行中学员的迁移策略。

### 10.3 数据

- 课程计划、单课、场景和学习任务建立稳定关联。
- 报表能区分内容版本。
- AI 编辑和 Skill 使用情况进入审计日志。
- 不把学员敏感数据作为 Skill 内容或生成提示词长期保存。

### 10.4 移动端

- 新增 scene 类型和课程层级不能破坏移动播放。
- 移动端不必复制完整编辑器，但必须支持连续课时导航、进度恢复和测验/PBL。

## 11. 测试与评测体系

### 11.1 工程测试

- 数据模型和迁移测试；
- Store adapter contract tests；
- API owner/role/RLS 测试；
- DSL 扩展字段金丝雀测试；
- AI 工具 schema 与 patch 测试；
- 编辑 undo/redo 和失败原子性测试；
- 桌面与移动 E2E；
- 导入、导出和离线播放回归。

### 11.2 AI 质量评测

建立稳定的黄金用例集：

| 维度 | 指标 |
|---|---|
| 引用准确性 | 是否只读取/修改指定对象 |
| 编辑成功率 | 指令完成且 schema 合法的比例 |
| 非目标修改率 | 未指定对象发生变化的比例，目标为 0 |
| 课程连贯性 | 目标覆盖、知识递进、重复率 |
| Skill 稳定性 | 同一 Skill 输出结构和风格的一致性 |
| 材料忠实度 | 生成内容是否能追溯并符合来源 |
| 可播放性 | 所有 scene 在桌面/移动端可正常运行 |

### 11.3 上线门槛

- P0/P1 级缺陷清零。
- 核心 E2E 全过。
- AI 修改非目标对象率为 0。
- 数据迁移有 dry-run 报告和回滚脚本。
- feature flag 已验证可关闭新路径。
- 产品负责人验收固定样本课程。

## 12. 分支、提交与发布策略

### 12.1 分支

建议每个 Phase 使用独立 `codex/` 或团队约定前缀分支，不建立跨数月的大一统分支。

```text
main
├─ alignment/infra-foundation
├─ alignment/course-references
├─ alignment/component-editing
├─ alignment/course-program
└─ alignment/skill-system
```

具体分支名前缀在启动时按团队协作工具统一；上图表达的是边界，不是立即创建分支的指令。

### 12.2 Commit 纪律

- 上游 cherry-pick 与 RJ 适配 commit 分开。
- 数据模型、迁移、业务接口和 UI 分开提交。
- 安全修复独立提交、独立测试。
- 不在功能 commit 中混入格式化全仓或无关清理。

### 12.3 发布

- 每阶段先内部 feature flag。
- 固定样本课程通过后开放给少量教师。
- 观察生成失败、编辑失败、保存冲突和学习记录异常。
- 稳定后再默认开启。

## 13. 风险登记

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 当前 Git 基线异常 | 无法可靠合并或回滚 | Gate 0 优先恢复完整历史和干净工作树 |
| Pro 1.0 与开源主线代码不一致 | 无法直接移植 | 以产品能力对齐为主，只依赖公开接口和开源 commit |
| RJ 扩展字段被上游 schema 丢弃 | 课程数据损坏 | registry、serialize、金丝雀测试、迁移 dry-run |
| AI 工具权限过大 | 误改课程或越权 | 显式引用、工具白名单、schema、owner/role、审计 |
| 课程级生成耗时和成本过高 | 用户等待、任务失败 | 异步分课生成、预算、暂停/重试、阶段模型路由 |
| Skill 组合不可控 | 输出漂移 | 类型化 manifest、冲突规则、固定评测、版本锁定 |
| 已发布课程被修改 | 学习记录错位 | 不可变版本快照、进行中学员迁移策略 |
| 桌面编辑能力破坏移动播放 | 学习端回归 | 移动 E2E 和 scene 兼容门禁 |
| 上游持续快速变化 | 重复建设 | 每阶段开始前做一次短周期 upstream audit |

## 14. 人力与排期建议

在 1 名主开发、1 名评审/测试支持的情况下：

| 阶段 | 预计时间 | 可独立上线 |
|---|---:|---|
| Gate 0 | 3–5 天 | 否，形成基线 |
| Phase 1 基础设施 | 2–3 周 | 是 |
| Phase 2 精确引用 | 2–3 周 | 是，优先级最高 |
| Phase 3 全组件编辑 | 3–4 周 | 可分组件上线 |
| Phase 4 课程级规划 | 3–4 周 | 是 |
| Phase 5 Skill 系统 | 3–4 周 | 可先官方 Skill 内测 |
| Phase 6 材料与风格迁移 | 3–4 周 | 可拆分上线 |

总体约 16–22 周。若多人并行，基础设施、AI 评测、组件编辑可以有限并行，但数据模型与权限契约必须由一条主线控制。

## 15. 推荐优先级与停止点

### 必做

1. Gate 0：整理基线。
2. Phase 1：存储、资产和安全基础。
3. Phase 2：精确引用。
4. Phase 3：Quiz/Interactive/PBL 受控编辑。
5. Phase 4：课程级规划。

### 第二优先级

6. 官方 Skill registry。
7. PPT 风格复用。
8. 音视频转课。

### 后置

9. 教学视频风格迁移。
10. 开放自定义 Skill 和市场化分发。

建议在 Phase 2 完成后设置第一个产品复盘点：如果精确引用已经显著提升教师编辑效率，可继续推进全组件编辑；若使用率不高，应先优化编辑入口，而不是直接扩大到复杂 Skill 系统。

第二个复盘点设在 Phase 4 完成后：根据多课生成的真实使用情况，决定 Skill 系统优先服务“课程生成标准化”还是“企业品牌模板”。

## 16. 启动时的第一周任务清单

当其他任务全部完成并正式宣布启动后，第一周只做以下工作：

1. 冻结并标记 Git 基线。
2. 更新上游 remote 信息和版本差异。
3. 盘点当前 DocumentStore、RuntimeStore、资产迁移和安全补丁状态。
4. 跑全量测试与固定课程样本。
5. 形成 1.0 能力矩阵：已有、半成品、缺失、明确不做。
6. 确认 Phase 1 的 cherry-pick/重写清单。
7. 确认 `CourseReference` 契约，但暂不同时施工 Skill 和课程级模型。
8. 输出第一阶段任务卡、负责人、依赖、验收和 feature flag。

完成以上八项并通过评审后，才进入代码实施。

## 17. 最终成功标准

对齐完成不以“界面看起来像 OpenMAIC 1.0”为标准，而以以下结果为准：

- 教师能通过显式引用让 AI 精确修改任意课程对象；
- Slide、Quiz、Interactive、PBL 都能安全地由 AI 编辑；
- 系统能规划、生成和发布连续多课时课程；
- 视觉和教学方法可通过版本化 Skill 复用；
- 所有新能力都接入账号、权限、学习任务、移动端和教学数据；
- 上游升级仍能以低风险方式持续吸收；
- 任一新路径失败时，课程数据和学员记录都可恢复且不会静默损坏。
