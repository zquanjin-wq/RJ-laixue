## 1. P0-1 修复：异步 tab-owner claim 协议（替换 v0.5 §1.4 全部伪代码）

### 1.1 v0.5 的两个硬伤

1. sessionStorage 已有 ownerId 时直接返回——复制标签页带着复制的 sessionStorage，
   永远不会做碰撞检测；
2. `while (Date.now() - start < 100)` busy-wait 阻塞事件循环，等待窗口内
   `onmessage` 不可能触发，碰撞协议必然检测不到占用。

### 1.2 修正后的异步协议

原则：winner 由 **instanceId 稳定排序** 决定，双方对同一组消息做同一计算，
因此恰好一方保留、另一方轮换；严禁 busy-wait。

```ts
// 每个 document 一个内存 instanceId（不写任何存储）
const INSTANCE_ID = generateHexId(16);
const OWNER_KEY = 'r3:tab:owner-id';

// 本 document 当前持有的 ownerId（内存真源；sessionStorage 只是 F5 恢复凭据）
let heldOwnerId: string | null = null;
const heldChannels = new Map<string, BroadcastChannel>();

type ClaimMsg =
  | { type: 'ping'; ownerId: string; instanceId: string }
  | { type: 'occupied'; ownerId: string; instanceId: string };

// 在 ownerId 的频道上监听：任何存活实例（持有者或竞争者）收到 ping 都应答
function attachListener(ownerId: string, channel: BroadcastChannel): void {
  channel.onmessage = (ev: MessageEvent<ClaimMsg>) => {
    const msg = ev.data;
    if (msg?.type === 'ping' && msg.ownerId === ownerId) {
      channel.postMessage({ type: 'occupied', ownerId, instanceId: INSTANCE_ID });
      // 我方若是持有者且对方排序更小（对方获胜），我方让出：
      // 不在此处直接改 sessionStorage，而是标记内存持有失效，
      // 下一次 getTabOwnerId() 会重新竞争新 owner（见 1.3 让出语义）
      if (heldOwnerId === ownerId && msg.instanceId < INSTANCE_ID) {
        heldOwnerId = null; // 让出；频道随后关闭
        channel.close();
        heldChannels.delete(ownerId);
      }
    }
  };
}

// Promise + timer 等待 100ms，绝不 busy-wait
function wait(ms: number): Promise<void> {
  return new Promise((resolve) => setTimeout(resolve, ms));
}

// 竞争一个 ownerId：返回 true = 我方赢得持有权
async function competeForOwner(ownerId: string): Promise<boolean> {
  const channel = new BroadcastChannel(`r3:tab:claim:${ownerId}`);
  attachListener(ownerId, channel);

  const responders = new Set<string>();
  const prevListener = channel.onmessage;
  channel.onmessage = (ev: MessageEvent<ClaimMsg>) => {
    prevListener?.(ev);
    const msg = ev.data;
    if (msg?.type === 'occupied' && msg.ownerId === ownerId) {
      responders.add(msg.instanceId);
    }
  };

  channel.postMessage({ type: 'ping', ownerId, instanceId: INSTANCE_ID });
  await wait(100); // 异步等待，事件循环正常派发 onmessage

  // 稳定排序：instanceId 字典序最小者胜。双方对同一 responder 集合做同一
  // 比较 → 恰好一个 winner。平局（同一 document 自己）不可能：instanceId
  // 是每 document 随机 16 byte。
  const winner = [...responders, INSTANCE_ID].sort()[0];
  if (winner === INSTANCE_ID) {
    heldOwnerId = ownerId;
    heldChannels.set(ownerId, channel); // 持有期间持续监听，应答后来的 ping
    return true;
  }
  channel.close();
  return false;
}

// 唯一入口（异步）。sessionStorage 命中也必须 ping 验证——F5 时旧 document
// 已退出、无 occupied 应答，自然保留；复制标签页时原 document 存活，必然碰撞。
async function claimTabOwnerId(): Promise<string> {
  if (heldOwnerId) return heldOwnerId; // 本 document 内存中仍持有

  const stored = sessionStorage.getItem(OWNER_KEY);
  if (stored && (await competeForOwner(stored))) return stored;

  for (let i = 0; i < 4; i++) {
    const candidate = generateHexId(16);
    if (await competeForOwner(candidate)) {
      sessionStorage.setItem(OWNER_KEY, candidate);
      return candidate;
    }
  }
  throw new Error('Failed to claim tabOwnerId after 4 attempts');
}
```

### 1.3 语义说明

- **F5 刷新**：旧 document 销毁（频道关闭），sessionStorage 保留。新 document
  对 stored ownerId ping 无应答 → 保留原 owner → 同 visit 续播（门禁 5 不变）。
- **复制标签页**：sessionStorage 被复制，但原 document 存活并应答 occupied。
  两方各自计算 winner = min(instanceId)：原 document 若败则 `heldOwnerId=null`
  让出，下次 `claimTabOwnerId()` 重新竞争新 owner；复制页若败则轮换新候选。
  恰好一方保留原 owner。
- **双方同时放弃不可能**：让出决策基于同一 responder 集合的同一排序。
- **持有者让出是安全的**：visit 的 tabOwnerId 只在 claimOrReuseVisitInTx 读取
  当前 owner；让出方下一次持久化会拿新 owner → 开新 visit，旧 visit 留在原
  owner 名下由 outbox 继续排空，不串数据。
- **残余风险声明**：100ms 窗口外到达的 occupied 应答不可知（极小概率两
  document 短暂共用 owner）。后果上限是两标签页写入同一 visit——与 v0.5 前
  行为相同，不破坏服务端数据完整性；不再收紧。

### 1.4 调用点同步修订

v0.5 §2.2 调用栈中 `getTabOwnerId().id` 同步改为：

```ts
const tabOwnerId = await claimTabOwnerId(); // 事务外 await，再进 Dexie 事务
return db.transaction('rw', [...], async () => {
  const visit = await claimOrReuseVisitInTx(stageId, tabOwnerId);
  // ...
});
```

注意：claim（含 100ms 等待）必须在 Dexie 事务**外**完成——事务内不得
插入跨 tick 等待，否则事务自动提交。

## 2. P0-2 修复：duplicate-complete preflight 前移 + 依赖方向修正
（替换 v0.5 §1.8 与 §2.5 步骤 4）

### 2.1 v0.5 的两个错误

1. **依赖方向反了**：v0.5 用
   `where('dependsOnEntryId').equals(completedStatusEntryId)` 找 append。
   真实关系是 `statusEntry.dependsOnEntryId = appendEntryId`（status 依赖
   append，R3.0 outbox.ts 已证实）。
2. **顺序错误**：v0.5 §2.5 先写 state、入队 append，之后才进 §1.8 检查
   completedStatusEntryId。重复 complete 时即使 eventId 相同，新 append
   已经留在 outbox，session completed 后收到 409。

### 2.2 修正：preflight 在所有写入之前

`persistSnapshotWithComplete` 事务内的执行顺序调整为：

```ts
return db.transaction('rw',
  [db.playbackVisits, db.playbackVisitStates, db.runtimeOutbox,
   db.runtimeChainHeads, db.succeededEntries], // succeededEntries 加入事务表集合
  async () => {
    const visit = await claimOrReuseVisitInTx(stageId, tabOwnerId);

    // ── PREFLIGHT（任何写入之前）────────────────────────────
    if (visit.completedStatusEntryId) {
      // (a) status 已有成功凭据 → 本 cycle 已终结
      const succeeded = await db.succeededEntries.get(visit.completedStatusEntryId);
      if (succeeded) {
        // claim 层不应再返回本 visit（见 §3.3 claim 过滤强化）；
        // 到达此处说明凭据在 claim 之后落定（竞态），直接按新 cycle 处理：
        // 抛出可识别错误，调用方以新 visit 重试本快照
        throw new VisitCycleCompletedError(visit.visitId);
      }

      const statusEntry = await db.runtimeOutbox.get(visit.completedStatusEntryId);
      if (statusEntry && snapshot.completed) {
        // (b) status 仍在 outbox：沿正确依赖方向找旧 append
        const prevAppend = statusEntry.dependsOnEntryId
          ? await db.runtimeOutbox.get(statusEntry.dependsOnEntryId)
          : undefined;

        if (prevAppend?.body?.id === `${visit.sessionId}:${snapshot.eventId}`) {
          // eventId 一致 → 幂等返回既有 IDs，零新入队、零 state 写入
          return {
            visitId: visit.visitId,
            appendId: prevAppend.id,
            statusId: statusEntry.id,
          };
        }
        // eventId 不一致且 status 未完成 → 在任何写入前拒绝
        throw new SnapshotEventMismatchError(visit.visitId, snapshot.eventId);
      }
      if (statusEntry && !snapshot.completed) {
        // complete 已在链上，后续普通快照不再入队（cycle 收尾中）：
        // 幂等返回，不写 state、不入队 append
        return { visitId: visit.visitId, appendId: undefined, statusId: statusEntry.id };
      }
      // statusEntry 不存在（已被 dead/清理）：罕见 race，放行重新入队
    }
    // ── PREFLIGHT 结束 ─────────────────────────────────────

    // 1. 写 visit-specific state（v0.5 §2.5 步骤 1 原文）
    // 2. ensure create entry（v0.5 §2.5 步骤 2 原文）
    // 3. append（v0.5 §2.5 步骤 3 原文）
    // 4. completed set_status：首次 complete 才到达这里，直接入队
    //    statusEntry.dependsOnEntryId = 本事务的 appendId（正确方向）
  }
);
```

### 2.3 关键不变量

- 重复 complete（同 eventId）：`runtimeOutbox` 条目数**零增长**，`playbackVisitStates`
  **零写入**，返回既有 append/status IDs；
- 重复 complete（异 eventId）：在任何写入前抛 `SnapshotEventMismatchError`，
  state 与 outbox 均不变；
- 依赖方向唯一真源：`statusEntry.dependsOnEntryId = appendEntryId`；
- complete 已入队后的普通快照：幂等空转，不再追加 append（防止 completed
  后 409 的第二条路径）。

## 3. P0-3 修复：legacy adoption 合法索引 + 接入 claim 调用链
（替换 v0.5 §5.2 adoption 伪代码与 §2.2 claim 步骤）

### 3.1 v0.5 的两个问题

1. `playbackVisits` 没有单字段 `stageId` 索引（v18 schema 只有
   `[stageId+status]` 与 `[tabOwnerId+stageId]`），`where('stageId')` 会在
   Dexie 运行时抛 SchemaError；
2. `adoptLegacyVisitInTx` 定义了但没有被 `claimOrReuseVisitInTx` 调用，
   adoption 永远不会发生。

### 3.2 修正：adoption 用已有复合索引，并作为 claim 第一步

```ts
// claimOrReuseVisitInTx 修正版（事务内）
async function claimOrReuseVisitInTx(stageId: string, tabOwnerId: string):
  Promise<PlaybackVisit> {
  // 0. legacy adoption（本事务内原子接管；必须是第一步）
  const adopted = await adoptLegacyVisitInTx(stageId, tabOwnerId);
  if (adopted) return adopted;

  // 1. 同 (stageId, tabOwnerId) active visit？（v0.5 原文）
  //    强化：completedStatusEntryId 已有成功凭据的 visit 不算 active
  const mine = await db.playbackVisits
    .where('[tabOwnerId+stageId]').equals([tabOwnerId, stageId])
    .filter(v => v.status === 'active')
    .first();
  if (mine) {
    if (mine.completedStatusEntryId) {
      const succ = await db.succeededEntries.get(mine.completedStatusEntryId);
      if (succ) {
        // cycle 已终结但 status 字段尚未翻转——视为 completed，落入新建分支
      } else {
        return mine;
      }
    } else {
      return mine;
    }
  }

  // 2. 创建新 visit（v0.5 原文）
  // ...
}

// adoption 修正版（事务内；使用已声明的 [stageId+status] 索引）
async function adoptLegacyVisitInTx(stageId: string, tabOwnerId: string):
  Promise<PlaybackVisit | null> {
  // 合法索引查询：active 状态槽里找 legacy visit
  const legacy = await db.playbackVisits
    .where('[stageId+status]').equals([stageId, 'active'])
    .filter(v => v.visitId === `legacy-${stageId}`)
    .first();
  if (!legacy) return null;          // 无 legacy 行
  if (!legacy.isLegacyAdopted) return null; // 已被其他标签页接管

  // completed 但无成功凭据的 legacy 行不得作为 active cycle 恢复：
  // 迁移时 status 已按 row.completed 落 'completed'，上面 [stageId+status]
  // 查 'active' 槽天然排除；此处再显式断言一次（防御迁移数据异常）
  if (legacy.status !== 'active') return null;

  // 原子接管：同事务 update——两个标签页的竞争事务在 Dexie 层串行，
  // 后执行者看到 isLegacyAdopted=false 而失败 → 恰好第一个标签页接管
  await db.playbackVisits.update(legacy.visitId, {
    isLegacyAdopted: false,
    tabOwnerId,
  });
  return { ...legacy, isLegacyAdopted: false, tabOwnerId };
}
```

### 3.3 关键不变量

- 查询只使用 v18 schema 已声明索引（`[stageId+status]`），**不新增索引**；
- legacy session identity 恒为 `pb:<stageId>`（v0.5 §5.2 不变）；
- adoption 是 `claimOrReuseVisitInTx` 的第一步，与持久化同事务——接管原子性
  由 Dexie 事务串行保证，恰好一个标签页成功；
- adoption 失败（无 legacy / 已被接管 / legacy 已 completed）→ 正常走
  既有 active 查询或新建 visit 路径；
- 接管后该 visit 沿用旧 outbox 链（旧 create/append 条目 sessionId 不变），
  未完成 cycle 由 outbox 继续排空。

## 4. 新增三个门禁（追加到 v0.5 §4，编号 17-19）

| # | 场景 | 期望 |
|---|------|------|
| 17 | **两个实例同时持有相同复制 ownerId 启动**（模拟复制标签页：两个 BroadcastChannel 参与方以不同 instanceId 竞争同一 ownerId） | 恰好 instanceId 字典序较小的一方保留原 ownerId，另一方轮换到新 ownerId；双方决策一致（无双方保留、无双方放弃）；全程无 busy-wait（测试用真实计时器，断言等待期间 onmessage 被处理） |
| 18 | **重复 complete preflight** | (a) 同 eventId 且 status 在 outbox：零新入队、零 state 写入，返回既有 append/status IDs——断言 `runtimeOutbox.count()` 前后不变；(b) 异 eventId 且 status 未完成：`SnapshotEventMismatchError`，state 与 outbox 均不变；(c) status 已有成功凭据：`VisitCycleCompletedError`，调用方换新 visit 后重试成功；(d) complete 在链上后的普通快照：幂等空转，不追加 append |
| 19 | **legacy adoption** | (a) adoption 查询不抛 Dexie SchemaError（使用 `[stageId+status]`）；(b) 两个标签页并发 adoption：恰好一个接管 legacy visit，另一个创建新 visit；(c) completed 无凭据的 legacy 行不被接管，调用方创建新 visit；(d) 接管后 visit.sessionId 恒为 `pb:<stageId>`，旧 outbox 条目不重发 |

v0.5 的 16 个门禁继续有效；其中门禁 14（复制标签页碰撞）的期望以本文 §1.2
协议为准（instanceId 排序定 winner）。
