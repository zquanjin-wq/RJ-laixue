## 一、E2E 第一次失败 (2026-08-04)

### 实际链路
| 阶段 | 服务端响应 |
|------|:--:|
| create | 201 ✅ |
| submitted | 201 ✅ |
| completed | 200 ✅ |
| reviewed | 409 ❌ INACTIVE_SESSION |
| archived | 未执行（依赖阻断）|

### 根因
客户端链顺序 `create→submit→completed→reviewed→archived` 与服务端生命周期不匹配：
服务端 `set_status(completed)` 之后拒绝 `append_record(:grade)` 返回 409。

### 服务端契约约束
- `append_record` 必须在 session 处于 `active` 状态时执行
- `set_status(completed)` 之后 session 进入只读模式
- 已签字的 R2 客户端行为 `create→submit→completed→reviewed→archived` 在 outbox 模式下被打破

---

## 二、修复 (commit 4a570ff1)

### 链顺序调整
- 旧：`create → submit → completed → reviewed → archived`
- 新：`create → submit → reviewed → completed → archived`

### 实现变更
| 函数 | 变更 |
|------|------|
| `quizSubmittedViaOutbox` | 入队 `create → submit`，链尾停在 submit（不再 set completed）|
| `quizReviewedViaOutbox` | 依赖 submit 链尾，入队 `grade → set_status completed`，链尾推进到 completed |
| `quizRetryViaOutbox` | 依赖 completed 链尾，入队 `set_status archived`，链尾推进到 archived |

### 关键不变量
- 所有 `append_record` 必须在 `set_status` 翻转之前完成
- `runtimeChainHeads` 表追踪链尾，与 `runtimeOutbox` 同 rw 事务原子更新
- `completed` 与 `archived` 使用 distinct semanticKey
