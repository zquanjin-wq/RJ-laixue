## 1. 问题陈述（来自 2026-08-05 回归）

### 1.1 复现链路

```
课程第一次播放 → 完成
→ 客户端 set_status(completed) 200 ✅
→ 用户重新进入课程
→ 客户端继续复用确定性 session id "pb:<stageId>"
→ append_record → 409 INACTIVE_SESSION
→ outbox 永久滞留，连续退避重试（已观察到至少 6 次）
```

### 1.2 根因（已确认）

服务端守护（`lib/server/runtime-store/pg.ts:322-327`）：
```ts
if (parent.status !== 'active') {
  throw new Error(
    `@openmaic/storage-pg: cannot append to session ${...} with status '${parent.status}' — ` +
    `records may only be appended to an active session`,
  );
}
```

→ 客户端 deterministic session identity 策略与服务端 session 生命周期状态不兼容。

### 1.3 R1/R2 为何未暴露

R1/R2 playback 是 fire-and-forget。客户端不等待响应，409 静默失败，仅入 telemetry。**outbox 模式下重试持续暴露问题**。

## 2. 客户端 session identity 语义学

### 2.1 当前模型

```
session id = "pb:<stageId>"
→ 每次课程全程使用同一 session
→ 服务端视角：单个会话持续累计 records
→ 完成后：append 全部被拒
```

### 2.2 隐含假设

设计稿隐含假设"一次访问 = 一个会话"。但产品语义是：
- 一次访问（一次打开）= 一个会话
- 重新进入 = 新的访问 = 新的会话

→ 与 chat/quiz 不同：playback 完成时往往用户会"再来一次"。

### 2.3 三种合理模型对比

| 模型 | session id 策略 | completed 后行为 | 优点 | 缺点 |
|------|---------------|----------------|------|------|
| **A. New session per visit** | `pb:<stageId>:<visitId>` 每次访问新 | 旧 session 永久归档；新 session 创建 | 服务端语义最清晰 | session 数量爆炸；服务端 quota 风险 |
| **B. Reopen completed session** | `pb:<stageId>` 不变；完成后 `set_status(active)` 重新打开 | status 在 active↔completed 间循环 | 服务端零冗余；append 可恢复 | 引入服务端新行为；与 quiz/chat 不对称 |
| **C. Discard post-completed snapshots** | `pb:<stageId>` 不变；客户端检测 completed 后丢弃 snapshot | outbox 不入队新 append | 最小改动 | 用户行为丢失（重看、跳场景无服务端记录）|

## 3. 推荐方案：模型 A（New session per visit）+ 客户端防护

### 3.1 推荐理由

- **服务端契约零变更**：沿用现有 status 转换
- **与 quiz/chat 对称**：quiz 已是 `qa:<stageId>:<sceneId>:<attemptId>`，session id 含 attemptId
- **数据完整性**：每次访问服务端独立 session，独立生命周期
- **观测性**：可用 session 数衡量访问次数

### 3.2 客户端实现

#### 3.2.1 新 session id 格式

```
session id = "pb:<stageId>:<visitId>"
visitId = 32-hex UUID（每次新访问时生成）
```

#### 3.2.2 触发 visit 边界

| 事件 | 行为 |
|------|------|
| 首次进入课程 | 生成 visitId；outbox 入队 create |
| 课程刷新（同一 stage） | 若本地有未发送的 shadowPending → 沿用当前 visitId；否则生成新 visitId |
| 课程首次 load 时 | 检查上次 visitId 的 status；如 completed → 新 visitId |
| 切换课程（不同 stage） | 新 visitId（stage 变更） |
| 同课内切换场景 | 同一 visitId |

#### 3.2.3 客户端持久化

`PlaybackStateRecord` 新增字段：
```ts
visitId?: string;          // 当前 session 使用的 visitId
previousVisitIds?: string[]; // 历史 visits（用于 session 切换时的级联 cleanup）
```

#### 3.2.4 outbox enqueue 路径

`shadowPlaybackProgressViaOutbox`：
1. 检查 `playbackState.visitId`
2. 若缺失或状态为 `completed` 状态机的终态 → 生成新 visitId
3. 构造 `sessionId = "pb:<stageId>:<newVisitId>"`
4. 写入新的 create_session + append_record 链

#### 3.2.5 完成判定

客户端"该 visit 完成"条件（沿用 R2.1）：
- `playbackState.completed === true` → 当前 visit 已 set_status completed
- 用户重新进入课程时，**仅当**本地存在新的 shadowPending 才使用新 visitId
- 若仅浏览无新进度 → 不入队，保留 completed visit

### 3.3 服务端零变更

继续接受当前 `pb:<stageId>`，但实际变为 `pb:<stageId>:<visitId>`。服务端无需感知。

### 3.4 配额影响估算

单用户完整重看一课：
- R3.1：1 个 session
- R3.1a：N 个 sessions（N = 用户重看次数）
- 服务端 quota 仍宽裕（每用户每会话）
- 若担心 quota：可对 visitId 设 7 天 TTL 自动归档

## 4. 替代方案对比（备选）

### 4.1 模型 B：Reopen completed session

服务端新增 `set_status(active)`（反向）。**不推荐**：
- 与 quiz/chat 状态机不对称
- 引入服务端新行为面
- 业务上"重看"是新的访问，不应"撤销完成"
- reopen 还可能与跨设备 sync 冲突

### 4.2 模型 C：客户端丢弃

客户端检测 completed 后不入队新 append。**不推荐**：
- 用户"重看"完全失去服务端痕迹
- 与 telemetry 期望不符
- 实现看似简单但语义丑陋

### 4.3 模型 D：服务端允许 completed 后追加

服务端放宽 `appendRecord` 的 active 检查。**明确不推荐**：
- 破坏 R2 已签字状态机契约
- 影响范围远大于客户端修复
- 已由 R3.2 chain reorder 印证：客户端适配优于服务端放宽

## 5. 与 R3.2 chain reorder 的关系

R3.2 quiz chain reorder 与本设计解决**不同问题**：

| 项 | R3.2 quiz | R3.1a playback |
|----|-----------|---------------|
| 问题 | 单 session 内 append_record 顺序 | 跨 session 的 session identity |
| 触发 | 提交+批改 | 完成后再进课 |
| 服务端 | append_record 后于 set_status(completed) 被拒 | 同上，但触发条件不同 |

两者都需要"客户端要感知会话生命周期"，但 R3.1a 引入了 session identity 的变更（visit id）。

## 7. 开放问题

### 7.1 visitId 持久化时机

何时生成新 visitId？
- 选项：每次 mount component 时
- 选项：每次 store 初始化时
- 选项：基于 `lastKnownCompletedAt` 比较

需要 PlaybackChromeRoot 用例设计。

### 7.2 历史 session 清理

老的 `pb:<stageId>` session 是否需要服务端归档？
- 当前设计：保留（仅新访问新建）
- 服务端 quota：长期累积需 cleanup 策略
- 不在本设计稿范围（属运行时运维问题）

### 7.3 双设备同访问并发

用户同时在两台设备打开同一课程 → 两个 visitId。
- 服务端两个独立 session
- 客户端各自记录
- 接受（与"两设备同时编辑"语义一致）
