## 1. 核心契约（v0.3 修订）

### 1.1 模型命名（沿用 v0.2）

"new session per completed playback cycle"

### 1.2 cycle 定义（沿用）

- 起点：本次 cycle 第一次有效持久化
- 终点：set_status completed 成功凭据落 succeededEntries

### 1.3 session id 格式（沿用）

```
session id = "pb:<stageId>:<visitId>"
visitId = 32-hex UUID
```

### 1.4 跨标签页强隔离（v0.3 新增强）

**问题**：v0.2 ensureVisitId 查到任意 active visit 即复用，无 tabOwner 区分。

**解决**：
1. **tab identity 稳定来源**：`sessionStorage` key `r3:tab:owner-id`（不存 localStorage，跨标签页不共享）
2. 每个标签页打开时生成 16-hex UUID 写入（不存在则创建）
3. 标签页关闭 → sessionStorage 清空 → 重新打开 → 新 identity
4. ensureVisitId 改为查 `(stageId, tabOwnerId)` 复合键

```ts
// 同一 stage 上不同 tabOwner 可各自有独立 active visit
async function ensureVisitId(stageId: string, tabOwnerId: string):
  Promise<{ visitId, sessionId }> {
  // 1. 查 (stageId, tabOwnerId) 的 active visit
  const existing = await db.playbackVisits
    .where('[stageId+tabOwnerId+status]')
    .equals([stageId, tabOwnerId, 'active'])
    .first();
  if (existing) return { visitId: existing.visitId, sessionId: existing.sessionId };

  // 2. 检查最近 cycle completedCredentialAt → 新 visit
  // 3. 全新 → 新 visit
}

function getTabOwnerId(): string {
  const KEY = 'r3:tab:owner-id';
  let id = sessionStorage.getItem(KEY);
  if (!id) {
    id = crypto.randomUUID().slice(0, 16);
    sessionStorage.setItem(KEY, id);
  }
  return id;
}
```

**意外崩溃处理**：
- sessionStorage 存于标签页进程，崩溃可能丢失 → 新 tabOwnerId
- 这是设计意图：崩溃后等同于"新标签页"，新 visit 隔离正确

### 1.5 completed 凭据关联（v0.3 新增强）

**问题**：v0.2 PlaybackVisit 无 completedStatusEntryId，无法关联凭据。

**解决**：completed 入队时**原子**写入 visit 行。

```ts
async function enqueueCompletedInTx(visitId, sessionId, prevEntryId) {
  return db.transaction('rw', db.runtimeOutbox, db.playbackVisits, async () => {
    const statusEntryId = await _qEnqueue({
      sessionId, op: 'set_status',
      semanticKey: `pb:completed:${visitId}`,
      body: { status: 'completed', updatedAt: new Date().toISOString() },
    }, prevEntryId);

    // 原子写入 visit 行的 completedStatusEntryId
    await db.playbackVisits.update(visitId, {
      completedStatusEntryId: statusEntryId,
    });

    return statusEntryId;
  });
}
```

drain 完成后，凭据检查用：
```ts
const cred = await db.succeededEntries.get(visit.completedStatusEntryId);
if (cred) {
  // 该 visit 真正完成
  await db.playbackVisits.update(visit.visitId, {
    status: 'completed',
    completedCredentialAt: cred.deletedAt,
  });
}
```

### 1.6 playbackState 改为复合主键（v0.3 新增强）

**问题**：v0.2 引入 visits 表但 playbackState 仍以 stageId 单行，跨标签页会覆盖。

**解决**：Dexie v18 把 playbackState 升级为 `[stageId+visitId]` 复合主键。

```ts
PlaybackStateRecord = {
  stageId: string;       // 复合主键第一段
  visitId: string;       // 复合主键第二段（v0.3 新增）
  sceneIndex, actionIndex, consumedDiscussions, capturedAt, sceneId,
  completed?: boolean,
  runtimeShadowEventId?: string,
  shadowPending?: { eventId, capturedAt },
  previousVisits?: Array<{ visitId, completedCredentialAt }>, // 已完成 visits
};
```

snapshot / shadowPending 与 visitId 绑定，杜绝跨 visit 数据串扰。

### 1.7 complete 入队改为全链同事务（v0.3 重大修订）

**问题**：v0.2 §2.3 提出"append 已发送后才触发 set_status"，留下 append 成功 → status 未入队之间的崩溃窗口。

**解决**（**沿用 R3.2 chain reorder 模式**）：
- create(active) → append_record → set_status(completed) **同事务入队**
- dependsOnEntryId 保证服务端发送顺序
- 不依赖客户端"先收到 append 200 再入队 status"

```ts
async function persistSnapshotWithComplete(
  stageId, visitId, sessionId, snapshot
): Promise<void> {
  return db.transaction('rw', db.runtimeOutbox, db.playbackVisits, async () => {
    let prevId: string | undefined;

    // 1. ensureSession create（active）—— 仅当该 visit 尚无 create entry
    const existingCreate = await db.runtimeOutbox
      .where('semanticKey').equals(`pb:create:${sessionId}`)
      .filter(e => e.status !== 'superseded' && e.status !== 'dead')
      .first();
    if (!existingCreate) {
      prevId = await _qEnqueue({
        sessionId, op: 'create_session',
        semanticKey: `pb:create:${sessionId}`,
        body: { id: sessionId, kind: 'playback', stageId,
                status: 'active', createdAt: now() },
      });
    } else {
      prevId = existingCreate.id;
    }

    // 2. append（snapshot 永远入队）
    const appendId = await _qEnqueue({
      sessionId, op: 'append_record',
      semanticKey: `pb:append:${sessionId}:${snapshot.eventId}`,
      body: { id: `${sessionId}:${snapshot.eventId}`,
              createdAt: snapshot.capturedAt, sceneId: snapshot.sceneId,
              payload: snapshot },
    }, prevId);

    // 3. 若 snapshot 是 completed 终态——同事务入队 status
    if (snapshot.completed) {
      const statusId = await _qEnqueue({
        sessionId, op: 'set_status',
        semanticKey: `pb:completed:${visitId}`,
        body: { status: 'completed', updatedAt: now() },
      }, appendId);
      // 原子记录到 visit
      await db.playbackVisits.update(visitId, {
        completedStatusEntryId: statusId,
      });
    }

    return appendId;
  });
}
```

**关键不变量**：
- create / append / set_status **永远同事务入队**（独立完成路径与 R3.2 quiz 同源）
- set_status completed 由客户端在入队时同步设置（不依赖网络反馈）
- append 即便中间崩溃，下次同 visit 重入时 ensureCreate 命中已发送条目，链式重入
- 崩溃后服务器视角：create(active)→append→completed 顺序到达（前提：依赖链正确）

### 1.8 完成判定（基于 visit.completedStatusEntryId）

```ts
async function checkVisitCompleted(visitId) {
  const visit = await db.playbackVisits.get(visitId);
  if (!visit?.completedStatusEntryId) return false;
  const cred = await db.succeededEntries.get(visit.completedStatusEntryId);
  if (!cred) return false;
  // 更新 visit 状态
  await db.playbackVisits.update(visitId, {
    status: 'completed',
    completedCredentialAt: cred.deletedAt,
  });
  return true;
}
```

cycle 切换判定 = `checkVisitCompleted(lastVisitId) === true`。

## 2. visitId 生成与切换流程（修订）

### 2.1 首次有效持久化（ensureVisitId）

沿用 v0.2 §2.1，但加 `tabOwnerId` 入参：

```ts
async function ensureVisitId(stageId: string, tabOwnerId: string):
  Promise<{ visitId, sessionId, isNewVisit: boolean }> {
  return db.transaction('rw', db.playbackVisits, db.playbackState, async () => {
    // 1. 查 (stageId, tabOwnerId, active)
    const active = await db.playbackVisits
      .where('[stageId+tabOwnerId]').equals([stageId, tabOwnerId])
      .filter(v => v.status === 'active')
      .first();
    if (active) {
      return { visitId: active.visitId, sessionId: active.sessionId, isNewVisit: false };
    }

    // 2. 查最近已 completed 的 visit（按 completedCredentialAt）
    const lastCompleted = await db.playbackVisits
      .where('[stageId+tabOwnerId]').equals([stageId, tabOwnerId])
      .filter(v => v.status === 'completed')
      .reverse().sortBy('completedCredentialAt');
    
    if (lastCompleted.length > 0) {
      // 上次 cycle 已完成 → 新 visit
      return _createNewVisit(stageId, tabOwnerId, false);
    }

    // 3. 无任何 visit → 全新
    return _createNewVisit(stageId, tabOwnerId, true);
  });
}

function _createNewVisit(stageId, tabOwnerId, isFirstVisit) {
  const visitId = crypto.randomUUID();
  const sessionId = `pb:${stageId}:${visitId}`;
  const now = new Date().toISOString();
  return db.playbackVisits.add({
    stageId, visitId, sessionId, tabOwnerId,
    status: 'active',
    createdAt: now,
    isFirstVisit,
  }).then(() => ({ visitId, sessionId, isNewVisit: true }));
}
```

### 2.2 persistSnapshotWithComplete 流程（v0.3 修订后）

```
1. getTabOwnerId() → tabOwnerId
2. ensureVisitId(stageId, tabOwnerId) → { visitId, sessionId }
3. persistSnapshotWithComplete(...) → 在同事务中入队 create+append+(completed)
4. 若 snapshot.completed：
   - 原子写入 visit.completedStatusEntryId
5. 调度 drain（scheduleNextDrain）
```

### 2.3 append 流程不再独立

v0.2 中"append 已发送后才触发 set_status"被删除。
所有 set_status 与其依赖的 append **同事务入队**，依赖链保证发送顺序。

### 2.4 切换场景（同 visit）

```ts
// 同一 visit 内切换场景，只入队 append，不入队新 create
async function appendWithinVisit(stageId, visitId, snapshot) {
  // ensureVisitId 已经保证同 visit（除非上次 completed）
  // 直接入队 append（create 已存在）
}
```

## 3. Legacy/Outbox 终结（v0.3 修订）

### 3.1 旧 `pb:<stageId>` 条目保持原 session identity（沿用 v0.2）

不可重新绑定到新 visitId。旧条目继续走 `pb:<stageId>` session。

### 3.2 INACTIVE_SESSION 永久终结规则

**前置条件**：服务端 errorCode 必须 **精确** 等于 `'INACTIVE_SESSION'`。

实现：在 dequeueOne 或 client 拦截层捕获 response.body.error.code：
- `error.code === 'INACTIVE_SESSION'` → 不可恢复 → 该 entry 永久 dead
- `error.code === 'IDEMPOTENCY_CONFLICT'` → 幂等冲突 → 视为成功（已有实现）
- 其他 409 → 临时错误 → 继续重试

```ts
function isPermanentFailure(responseBody: any): boolean {
  return responseBody?.error?.code === 'INACTIVE_SESSION';
}

// 在 outbox 处理 response 时
if (response.status === 409 && isPermanentFailure(parsedBody)) {
  // 永久 dead（不可恢复）
  await markDead(entryId, 'INACTIVE_SESSION_permanent');
}
```

**deadReason 字段**：v0.2 提议为 `string`，v0.3 收紧为 enum：

```ts
type DeadReason =
  | 'INACTIVE_SESSION_permanent'  // 服务端完成，新 append 不可恢复
  | 'IDEMPOTENCY_CONFLICT_permanent'  // 实际场景很少，但需明确
  | 'TIMEOUT_EXCEEDED'             // 重试耗尽
  | 'CASCADE_DEAD'                 // 依赖链上游 dead
  | 'SCHEMA_INVALID'               // 服务端拒绝格式
  | 'OTHER_4XX'                    // 兜底
  | null;                          // 未终结
```

### 3.3 markDead 实现

```ts
async function markDeadInTx(entryId: string, reason: DeadReason): Promise<void> {
  await db.runtimeOutbox.update(entryId, {
    status: 'dead',
    deadReason: reason,
    deadAt: new Date().toISOString(),
  });
  // 级联依赖者
  const deps = await db.runtimeOutbox.where('dependsOnEntryId').equals(entryId)
    .filter(e => e.status === 'pending' && !e.leaseOwner).toArray();
  for (const d of deps) {
    await markDeadInTx(d.id, 'CASCADE_DEAD');
  }
}
```

### 3.4 telemetry 上报（含 deadReason）

沿用 R3.0 telemetry `reportTelemetry('runtime_shadow', { outcome, ... })`。

新增 outcome：
- `dead_inactive_session` — INACTIVE_SESSION 永久终结
- `dead_cascade` — 依赖链 dead
- `dead_timeout` — 重试耗尽

deadReason 字段加入 telemetry payload。

**注意**：client-diagnostics 400 阻断会影响 telemetry 上报。第②份设计稿（diagnostics 契约）解决此问题。在那之前，deadReason 上报路径未验证不破坏现有遥测流。

### 3.5 死链终结不会阻断新 visit

旧 `pb:<stageId>` 死链与新 `pb:<stageId>:<newVisitId>` 完全独立：
- 不同 sessionId
- 不同 outbox 条目集
- 不同 runtimeChainHeads
- 不同 playbackVisits 行

新 visit 在 visits 表新建行，不读旧 entries。
旧 entry 一旦 markDead，scheduler 不再尝试。

## 4. E2E 门禁（v0.3 修订，统一为 13 个场景）

| # | 场景 | 期望 |
|---|------|------|
| 1 | 首次进入课程，播放 3 个场景 | outbox 全部 201，最终 completed 200 |
| 2 | 首笔快照即 completed（用户打开即拉到末页） | create(active)→append→completed 同事务入队 |
| 3 | completed 成功后重新进入课程 | 新 visitId（不同 tabOwnerId 同 stage），append 201 |
| 4 | completed PATCH 失败后刷新 | 同 visitId 重试，set_status 同 session |
| 5 | F5 刷新（无新动作） | visitId 不变；outbox 排空后不创建新 visit |
| 6 | 课程中切场景（同 visit） | 同 sessionId，append 201 |
| 7 | 旧 pb:<stageId> 失败条目不阻断新 visit | 新 visit 独立完成；旧条目 dead |
| 8 | 同 stage 两标签页并发播放 | 两 tabOwnerId 各自有独立 visit，**snapshot 不串** |
| 9 | 刷新后成功条目不复活 | 已 succeededEntries 的 entry 不重发 |
| 10 | outbox 排空 + completedCredentialAt 落 succeededEntries | 下个 cycle 启动 |
| 11 | 关闭浏览器重新打开（同 profile） | 新 tabOwnerId → 新 visit，visits 表持久化 |
| 12 | 旧 cycle 未完成时用户产生新动作 | 不轮换；continue 当前 visit |
| 13 | **两标签页快照绝不串 visit** | playbackState 按 [stageId+visitId] 隔离 |

**13 个场景**，覆盖评审要求的全部。

### 5.2 迁移路径 v17→v18

**问题**：旧 playbackState 行主键是 stageId（单字段），新 schema 要求 [stageId+visitId]。

**解决**：迁移步骤
1. 读所有旧 playbackState 行
2. 派生 visitId = `legacy-${stageId}`（旧逻辑下 visitId 是隐式的）
3. 写入新 playbackState（以 [stageId+visitId] 为键）
4. 删除旧 stageId 单键行
5. 新建 playbackVisits 行：
   - visitId = `legacy-${stageId}`
   - tabOwnerId = `legacy-unknown`
   - status = currentRow.completed ? 'completed' : 'active'
   - 如果 completed，凭据状态未知（迁移窗口期）

**重要**：迁移后旧 playbackState 行被销毁，旧 runtimeOutbox 条目与 visits 关联需重建（**不在范围**，详见 §6）。

### 5.3 runtimeOutbox 字段扩展（v0.3 新增）

```ts
RuntimeOutboxEntry = {
  ..., // v17 fields

  deadAt?: string;

```

Dexie schema 不需改（可选字段），但 unit 测试覆盖 deadReason 写入。

## 6. 不在范围（v0.3 明确）

- 旧 `pb:<stageId>` outbox 条目到新 visits 表的反向迁移
  - 理由：旧条目 session identity 保持原状（§3.1），无需迁移到 visits 表
  - 影响：旧条目 status 检查只能用 sessionId 字段，不能用 visits 表
- visitId 与用户身份关联
- 跨设备 sync
- 服务端 quota
- telemetry 字段扩展细节（受第②份设计稿约束）

## 7. 与 R3.2 chain reorder 关系（修订）

| 项 | R3.2 quiz | R3.1a playback (v0.3) |
|----|-----------|----------------------|
| 服务端约束 | append_record 在 completed 后被拒 | 同 |
| 客户端方案 | chain reorder：所有 append 在 status 翻转前 | visitId 隔离 + 同样 reorder |
| 解决路径 | 单 session 内顺序调整 | 跨 session 隔离 + 同 session 内顺序调整 |
| **共契约** | create 永远 active，append 在前，set_status 在后 | **同** |

**关键复用**：v0.3 §1.7 persistSnapshotWithComplete **直接复用 R3.2 的"append 在前、status 在后"模式**，应用到 playback 的 create 链路。

## 8. quota 影响（仅记录）

- visits 表每行 ≈ 200 字节
- 用户每完成一课 +1 行（含 completed 状态）
- 假设平均每个用户完成 50 课：50 行/用户 = 10 KB/用户
- 大量用户活跃 → visits 表行数线性增长
- 不在本设计稿提出 TTL（评审要求）
