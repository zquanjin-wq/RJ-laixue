## 1. 核心契约（v0.4 修订）

### 1.1 模型命名（沿用）

"new session per completed playback cycle"

### 1.2 cycle 定义（沿用）

- 起点：本次 cycle 第一次有效持久化
- 终点：set_status completed 成功凭据落 succeededEntries

### 1.3 session id 格式（沿用）

```
session id = "pb:<stageId>:<visitId>"
```

### 1.4 tabOwnerId 生成与隔离（v0.4 修订）

**问题**：
- `crypto.randomUUID().slice(0, 16)` 包含 `-`（UUID hex 第 13 位），不是纯 hex
- sessionStorage 可被 `window.open` 创建的新上下文复制

**解决**：
```ts
function getTabOwnerId(): { id: string; isFresh: boolean } {
  const KEY = 'r3:tab:owner-id';
  const CLAIMED_KEY = 'r3:tab:owner-claimed';
  let id = sessionStorage.getItem(KEY);
  let claimedAt = sessionStorage.getItem(CLAIMED_KEY);

  if (!id || !claimedAt) {
    id = generateHexId(16);  // 32 hex chars
    sessionStorage.setItem(KEY, id);
    sessionStorage.setItem(CLAIMED_KEY, Date.now().toString());
    return { id, isFresh: true };
  }

  // 碰撞检测：如果 duplicates 出现，重新生成
  return { id, isFresh: false };
}

function generateHexId(byteLen: number): string {
  const buf = new Uint8Array(byteLen);
  crypto.getRandomValues(buf);
  return Array.from(buf, (b) => b.toString(16).padStart(2, '0')).join('');
}
```

**tab-owner claim 机制**：
- sessionStorage 可被复制（opener、复制标签页）→ 简单读取不可信
- 必须在 Dexie visits 表中加 claim 字段 + 验证逻辑

```ts
interface PlaybackVisit {
  visitId: string;          // PK（全局 UUID，32 hex）
  stageId: string;
  tabOwnerId: string;       // 16-byte hex
  sessionId: string;
  status: 'active' | 'completed';
  createEntryId?: string;   // 创建时原子写入
  completedStatusEntryId?: string;
  createdAt: string;
  createdByOwnerAt: string;  // tab 启动时间戳
  completedCredentialAt?: string;
}
```

**claim 验证**：
```ts
async function claimOrReuseVisit(stageId, tabOwnerId): Promise<PlaybackVisit> {
  return db.transaction('rw', db.playbackVisits, async () => {
    // 1. 当前 tab 是否已有 active visit
    const mine = await db.playbackVisits
      .where('tabOwnerId').equals(tabOwnerId)
      .filter(v => v.stageId === stageId && v.status === 'active')
      .first();
    if (mine) return mine;

    // 2. 该 stage 下其他 tab 的 active visit 存在 → 不共享，新建
    // （不删除他人 visit，仅避免复用）
    const stageActive = await db.playbackVisits
      .where('stageId').equals(stageId)
      .filter(v => v.status === 'active')
      .count();
    
    // 3. 新建 visit
    const visitId = crypto.randomUUID();
    const sessionId = `pb:${stageId}:${visitId}`;
    const now = new Date().toISOString();
    const visit: PlaybackVisit = {
      visitId, stageId, tabOwnerId, sessionId,
      status: 'active',
      createdAt: now,
      createdByOwnerAt: now,
    };
    await db.playbackVisits.add(visit);
    return visit;
  });
}
```

**为什么不开 index**：`where('tabOwnerId').equals(...)` 不要求索引（Dexie 支持 indexed/non-indexed）。如果性能需要，再加 `[tabOwnerId+stageId+status]` 索引。

### 1.5 完成判定（基于 visit.completedStatusEntryId）

沿用 v0.3 §1.8。`checkVisitCompleted(visitId)`：
- visit.completedStatusEntryId 必须存在
- succeededEntries[visit.completedStatusEntryId] 必须存在
- 更新 visit.status='completed' 与 completedCredentialAt

### 1.6 visitId 全局唯一主键（v0.4 修订）

**问题**：v0.3 用 `[stageId+visitId]` 复合主键，但代码用 `db.playbackVisits.get(visitId)`，不匹配。

**解决**：visitId 全局 UUID（32 hex 含 `-`），作为 visits 表单一主键。索引按需建：

```ts
this.version(18).stores({
  ...
  playbackVisits: 'visitId, [stageId+status], [tabOwnerId+stageId], completedCredentialAt',
});
```

- 主键：`visitId`（全局 UUID）
- 复合索引：用于查询优化
- 所有 `db.playbackVisits.get(visitId)` 直接命中

### 1.7 visit-specific snapshot/state 表（v0.4 修订）

**问题**：v0.3 把 playbackState 主键改成 [stageId+visitId]，Dexie 不能原地迁移 object store。

**解决**：新增 `playbackVisitStates` 表，独立存 visit-specific 数据。**保留**旧 `playbackState` 作为 legacy 源（仅读取，已不再写入）。

```ts
this.version(18).stores({
  ...
  // 旧 playbackState 不变（仍是 stageId 单键，标记为 legacy）
  playbackState: 'stageId',
  // 新增 visit-specific state
  playbackVisitStates: 'visitId, [stageId+visitId]',
});
```

```ts
interface PlaybackVisitState {
  visitId: string;          // PK
  stageId: string;
  sceneIndex: number;
  actionIndex: number;
  consumedDiscussions: string[];
  updatedAt: number;
  sceneId?: string;
  capturedAt?: string;
  completed?: boolean;
  runtimeShadowEventId?: string;
  shadowPending?: { eventId, capturedAt };
}
```

**previousVisits 删除**（v0.3 提议）：信息冗余，独立 visits 表已承载，无限增长风险。

**legacy playbackState 保留**：
- 仅旧版本迁移期可读
- 旧 stageId 单行内容 = 最近一次有效 visit 的快照副本
- 不写入新内容
- v19 或后续版本可删（独立签字卡）

### 1.8 create/completed 身份持久化与 CAS（v0.4 新增强）

**问题**：v0.3 completedStatusEntryId 写入 visit，但 create status 未持久化；且恢复时可能错判。

**解决**：PlaybackVisit 同时持久化 create 与 completed 的 outbox entry ID。

```ts
// 入队 create 时
const createEntryId = await _qEnqueue({ ... });
await db.playbackVisits.update(visitId, { createEntryId });

// 入队 set_status completed 时（CAS）
await db.transaction('rw', db.runtimeOutbox, db.playbackVisits, async () => {
  const visit = await db.playbackVisits.get(visitId);
  if (visit.completedStatusEntryId) {
    // 已有 completed entry，禁止覆盖
    // （重复 complete 入队 → 检查 visits.completedStatusEntryId 是否已存在）
    return;  // 或者抛错
  }
  const statusEntryId = await _qEnqueue({ ... });
  await db.playbackVisits.update(visitId, { completedStatusEntryId: statusEntryId });
});
```

**恢复时检查**：
```ts
async function restoreVisit(visit) {
  // 1. createEntryId 检查
  if (visit.createEntryId) {
    const stillPending = await db.runtimeOutbox.get(visit.createEntryId);
    const succCred = await db.succeededEntries.get(visit.createEntryId);
    if (!stillPending && !succCred) {
      // create 已不在 outbox/succeeded → 异常
      // 但只通过 semanticKey 查也无法准确判定 → 用 entryId 检查
    }
  }
  // 2. completedStatusEntryId 同理
}
```

**重复 complete 保护**：
- 第二次 enqueue completed 时，事务内检查 visit.completedStatusEntryId 已存在 → 拒绝
- 防止重复 complete 覆盖原 entry ID

### 1.9 DeadReason enum（v0.4 收窄）

**移除** v0.3 中尚未实现支持的：
- `TIMEOUT_EXCEEDED` — 重试上限未实现，删除
- `OTHER_4XX` — 兜底过于宽泛，删除
- `SCHEMA_INVALID` — 服务端无 schema 校验反馈，删除

**保留**：
```ts
type DeadReason =
  | 'INACTIVE_SESSION_permanent'  // append_record/session 已 completed
  | 'IDEMPOTENCY_CONFLICT_permanent'  // 已签 v0.3 注：实际递归 dead，不视为成功
  | 'CASCADE_DEAD';               // 依赖链上游 dead
```

### 1.10 IDEMPOTENCY_CONFLICT 语义纠正

v0.3 §3.2 误写"视为成功"。**纠正**：

依据 `lib/server/runtime-store/http-error.ts` 与 R3.0 已签状态机：
- `IDEMPOTENCY_CONFLICT` = 同 record id 但内容不同 → **永久 dead**（递归级联下游）
- 这是"客户端与服务端状态不一致"信号，不应静默成功

文档历史错误修正，行为不变。

## 2. persistSnapshotWithComplete 流程（v0.4 修订）

### 2.1 入参

```ts
async function persistSnapshotWithComplete(
  stageId: string,
  snapshot: {
    eventId: string;
    capturedAt: string;
    sceneId?: string;
    sceneIndex: number;
    actionIndex: number;
    consumedDiscussions?: string[];
    completed?: boolean;
  }
): Promise<{ visitId, appendId, statusId? }>
```

### 2.2 全表同事务入队（v0.4 重大修订）

**事务范围**（一次性）：
- `playbackVisits`
- `playbackVisitStates`（visit-specific snapshot）
- `runtimeOutbox`
- `runtimeChainHeads`
- `succeededEntries`（CAS 时不写，仅查）

```ts
return db.transaction(
  'rw',
  [db.playbackVisits, db.playbackVisitStates, db.runtimeOutbox, db.runtimeChainHeads],
  async () => {
    // 1. claim or reuse visit
    const visit = await claimOrReuseVisit(stageId, getTabOwnerId().id);
    
    // 2. snapshot 写入 visit-specific state
    await db.playbackVisitStates.put({
      visitId: visit.visitId,
      stageId,
      sceneIndex: snapshot.sceneIndex,
      actionIndex: snapshot.actionIndex,
      consumedDiscussions: snapshot.consumedDiscussions ?? [],
      sceneId: snapshot.sceneId,
      capturedAt: snapshot.capturedAt,
      updatedAt: Date.now(),
      completed: snapshot.completed,
      runtimeShadowEventId: snapshot.eventId,
      shadowPending: { eventId: snapshot.eventId, capturedAt: snapshot.capturedAt },
    });
    
    // 3. create entry（仅当该 visit 尚无 create）
    let prevId: string | undefined = visit.createEntryId;
    if (!prevId) {
      const createEntryId = await _qEnqueue({
        sessionId: visit.sessionId, op: 'create_session',
        semanticKey: `pb:create:${visit.sessionId}`,
        body: { id: visit.sessionId, kind: 'playback', stageId,
                status: 'active', createdAt: snapshot.capturedAt },
      });
      prevId = createEntryId;
      await db.playbackVisits.update(visit.visitId, { createEntryId });
    }
    
    // 4. append entry（always）
    const appendId = await _qEnqueue({
      sessionId: visit.sessionId, op: 'append_record',
      semanticKey: `pb:append:${visit.sessionId}:${snapshot.eventId}`,
      body: { id: `${visit.sessionId}:${snapshot.eventId}`,
              createdAt: snapshot.capturedAt, sceneId: snapshot.sceneId,
              payload: { v: 1, sceneIndex: snapshot.sceneIndex,
                         actionIndex: snapshot.actionIndex,
                         consumedDiscussions: snapshot.consumedDiscussions ?? [],
                         capturedAt: snapshot.capturedAt } },
    }, prevId);
    
    // 5. 完成时入队 set_status + CAS
    let statusId: string | undefined;
    if (snapshot.completed && !visit.completedStatusEntryId) {
      statusId = await _qEnqueue({
        sessionId: visit.sessionId, op: 'set_status',
        semanticKey: `pb:completed:${visit.visitId}`,
        body: { status: 'completed', updatedAt: snapshot.capturedAt },
      }, appendId);
      await db.playbackVisits.update(visit.visitId, { completedStatusEntryId: statusId });
    } else if (snapshot.completed && visit.completedStatusEntryId) {
      // 重复 complete → 拒绝（CAS 失败）
      throw new Error(`duplicate complete for visit ${visit.visitId}`);
    }
    
    return { visitId: visit.visitId, appendId, statusId };
  }
);
```

**关键不变量**：
- snapshot / state / outbox / chain head 同事务原子提交
- 任意步骤失败 → 整事务回滚
- 重复 complete → CAS 拒绝

### 2.3 drain 完成后凭证更新

drain 后（沿用 R3.1 已实现的 cleanup）：
- 检出 visit.completedStatusEntryId 在 succeededEntries 中
- 更新 visit.status='completed' + completedCredentialAt

### 2.4 切换场景（同 visit）

同 visit 内切换场景，只调用 `persistSnapshotWithComplete`（snapshot.completed=false），不入队新 create。

### 3.2 409 响应格式与分类（v0.4 修订）

**复用 R3.0 工具**：
```ts
import { extractErrorCode } from '@/lib/runtime/outbox';  // 已签 R3.0 工具

function isPermanentFailure(responseBody: any): boolean {
  const code = extractErrorCode(responseBody);
  return code === 'INACTIVE_SESSION' || code === 'IDEMPOTENCY_CONFLICT';
}
```

**错误码语义**：
| errorCode | 含义 | 客户端处置 |
|-----------|------|----------|
| `INACTIVE_SESSION` | session 已非 active | **永久 dead** + 终结下游 |
| `IDEMPOTENCY_CONFLICT` | 同 id 不同内容 | **永久 dead**（递归） |
| 其他 4xx（如 `MISSING_REQUIRED_FIELD`） | 客户端 bug | 暂时按临时错处理，监控告警 |
| 5xx | 服务端临时错误 | 退避重试 |

**deadReason 写入**：
```ts
if (isPermanentFailure(body)) {
  const code = extractErrorCode(body);
  const reason: DeadReason =
    code === 'INACTIVE_SESSION' ? 'INACTIVE_SESSION_permanent' :
    code === 'IDEMPOTENCY_CONFLICT' ? 'IDEMPOTENCY_CONFLICT_permanent' :
    'INACTIVE_SESSION_permanent';  // 兜底（实际不应到这）
  await markDeadInTx(entryId, reason);
}
```

## 4. E2E 门禁（v0.4 修订，统一为 15 个场景）

| # | 场景 | 期望 |
|---|------|------|
| 1 | 首次进入课程，播放 3 个场景 | outbox 全部 201，最终 completed 200 |
| 2 | 首笔快照即 completed（打开即拉到末页） | create(active)→append→completed 同事务入队 |
| 3 | **同一标签页**完成后重新播放 | **同 tabOwnerId、新 visitId**（修订 v0.3 表述）|
| 4 | completed PATCH 失败后刷新 | 同 visitId 重试，set_status 同 session |
| 5 | F5 刷新（无新动作） | visitId 不变；outbox 排空后不创建新 visit |
| 6 | 课程中切场景（同 visit） | 同 sessionId，append 201 |
| 7 | 旧 pb:<stageId> 失败条目不阻断新 visit | 新 visit 独立完成；旧条目 dead |
| 8 | 同 stage 两标签页并发播放 | 两 tabOwnerId 各自独立 visit，**snapshot 不串** |
| 9 | 刷新后成功条目不复活 | 已 succeededEntries 的 entry 不重发 |
| 10 | outbox 排空 + completedCredentialAt 落 succeededEntries | 下个 cycle 启动 |
| 11 | 关闭浏览器重新打开（同 profile） | 新 tabOwnerId → 新 visit，visits 表持久化 |
| 12 | 旧 cycle 未完成时用户产生新动作 | 不轮换；continue 当前 visit |
| 13 | 两标签页快照绝不串 visit | playbackVisitStates 按 visitId 隔离 |
| 14 | **复制标签页（opener）owner 碰撞检测** | 复制后 tabOwnerId 检测到 claim，**新建 visit** |
| 15 | **v17→v18 数据无损迁移** | 旧 playbackState 行被读取后写入新 playbackVisitStates，**不丢失** |
| 16 | **重复 complete 不覆盖 entry ID** | 第二次 enqueue complete → CAS 拒绝 |

15 个场景（+1 旧场景 #16）覆盖评审要求全部。

### 5.2 v17→v18 迁移路径

**问题**：v0.3 提出"派生 visitId = `legacy-${stageId}`"，但 Dexie 实际无法原地把 stageId 单键转 [stageId+visitId]。

**v0.4 解决**：不修改旧表，新增独立表。

```ts
// upgrade 函数（v17 → v18）
await this.version(18).upgrade(async (tx) => {
  // 1. 读旧 playbackState 所有行
  const oldRows = await tx.table('playbackState').toArray();
  
  // 2. 派生 visitId（每个 stageId 一个 legacy visit）
  const legacyVisits: PlaybackVisit[] = oldRows.map(row => ({
    visitId: `legacy-${row.stageId}`,  // deterministic legacy ID
    stageId: row.stageId,
    tabOwnerId: 'legacy-unknown',
    sessionId: `pb:${row.stageId}:legacy-${row.stageId}`,
    status: row.completed ? 'completed' : 'active',
    createdAt: new Date(row.updatedAt || Date.now()).toISOString(),
    createdByOwnerAt: new Date(row.updatedAt || Date.now()).toISOString(),
    // completedCredentialAt 不可知（迁移窗口期）
  }));
  await tx.table('playbackVisits').bulkAdd(legacyVisits);
  
  // 3. 把旧 playbackState 行复制到 playbackVisitStates
  const newStates: PlaybackVisitState[] = oldRows.map(row => ({
    visitId: `legacy-${row.stageId}`,
    stageId: row.stageId,
    sceneIndex: row.sceneIndex,
    actionIndex: row.actionIndex,
    consumedDiscussions: row.consumedDiscussions ?? [],
    sceneId: row.sceneId,
    capturedAt: row.capturedAt,
    updatedAt: row.updatedAt,
    completed: row.completed,
    runtimeShadowEventId: row.runtimeShadowEventId,
    shadowPending: row.shadowPending,
  }));
  await tx.table('playbackVisitStates').bulkAdd(newStates);
  
  // 4. 旧 playbackState 行不删除（v19+ 另案清理）
});
```

**数据完整性**：
- 旧 playbackState 行被复制，**不删**
- 旧 runtimeOutbox 条目不受影响（仍按 session id 关联）
- visits / visitStates 通过 `legacy-${stageId}` visitId 关联旧数据

## 7. 与 R3.2 chain reorder 关系

| 项 | R3.2 quiz | R3.1a playback (v0.4) |
|----|-----------|----------------------|
| 服务端约束 | append_record 在 completed 后被拒 | 同 |
| 客户端方案 | chain reorder：所有 append 在 status 翻转前 | visitId 隔离 + 同模式 |
| 共契约 | create 永远 active，append 在前，set_status 在后 | **同**（v0.4 §2.2 直接复用 R3.2 模式）|

## 8. quota 影响（仅记录）

- playbackVisits 每行 ≈ 200 字节
- playbackVisitStates 每行 ≈ 300 字节
- 每用户每完成一课 = 一行 visit + 一行 state
- 假设平均完成 50 课：50 × 500B = 25 KB/用户
- 不在本设计稿提出 TTL
