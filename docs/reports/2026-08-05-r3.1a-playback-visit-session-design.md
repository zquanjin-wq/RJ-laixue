## 1. 核心概念（修订）

### 1.1 模型命名澄清

**新称谓**：模型 A = **"new session per completed playback cycle"**

**不再使用**："new session per visit" — 这个说法歧义，F5 不应换 session。

### 1.2 cycle 定义

```
"playback cycle" = 同一组 (stageId, visitId) 内从 create 到 completed 的完整序列
```

cycle 边界：
- **起点**：本次 cycle 第一次产生有效持久化动作时
- **终点**：当前 cycle 的 completed PATCH 成功凭据落 succeededEntries

**关键不变量**：
- 同一 cycle 内的所有 record 共享同一 session id = `pb:<stageId>:<visitId>`
- cycle 完成的判定 = `set_status completed` 成功凭据（不是本地 `playbackState.completed` 字段）
- 下一 cycle 仅在上一个 cycle completed 成功凭据成立后 + 用户产生下一次有效播放动作时启动

### 1.3 何时轮换 visitId

| 场景 | 行为 | 依据 |
|------|------|------|
| 首次进入课程 | 在第一次有效持久化时创建 visitId | §1.5 原子入队 |
| F5 刷新（无新持久化） | 复用现有 visitId | 不因 F5 制造新 cycle |
| 刷新（有 pending 未发送） | 复用同一 visitId | cycle 未结束 |
| 刷新（completed cycle 且无新动作） | 复用 visitId | 无新动作不算新 cycle |
| 用户产生下一个有效动作（且当前 cycle 已 completed） | 新 visitId | cycle 边界 |
| 同课内切换场景 | 同一 visitId | 不产生 cycle 切换 |

### 1.4 跨标签页归属（评审拍板方向 B）

**采用方案**：独立 `playbackVisits` 表，主键 `[stageId+visitId]`。

理由：
- 同一 stage 在不同标签页可能并行浏览
- 单行 `playbackState`（以 stageId 为主键）无法承载并发归属
- 多活动 visit 可共存，每个标签页持有自己的 visitId

数据模型：
```ts
// Dexie v18
PlaybackVisit = {
  stageId: string;        // 复合主键第一段
  visitId: string;        // 32-hex UUID
  sessionId: string;      // = "pb:<stageId>:<visitId>"
  status: 'active' | 'completed';  // 本地视角
  completedCredentialAt?: string;  // 服务端 completed 成功凭据时间
  lastAppendId?: string;  // 最近成功 append 的 outbox entry id
  tabOwnerId?: string;    // 创建该 visit 的标签页标识（best-effort，崩溃可能漂移）
  createdAt: string;
};
```

playbackState 表简化：
```ts
PlaybackStateRecord = {
  stageId: string;        // PK
  sceneIndex, actionIndex, ...  // 不变
  visitId?: string;        // 当前标签页正在用的 visit（迁移旧数据后保留兼容）
  previousVisitIds?: string[]; // 已 completed 的历史 visits
};
```

### 1.5 严格顺序不变量（create 永远 active）

新不变量：**create 永远以 status='active' 创建，绝不直接创建 completed session。**

实现：
```ts
async function enterVisit(stageId, tabId) {
  // 在 Dexie rw 事务内原子完成：
  // 1. 查 stageId 上次成功凭据
  // 2. 若上次是 completed → 创建新 visit + 新 active session
  // 3. 若上次是 active 或无记录 → 复用当前 visit
  // 4. 返回当前 sessionId
}
```

首次 create 永远 `status: 'active'`，append 在前，set_status 在后。

### 1.6 完成判定（必须基于成功凭据）

本地 `playbackState.completed` 字段不可作为 cycle 完成判定（仅是 UI 提示）。

**真实完成判定**：
- `outbox` 中该 cycle 的 `set_status completed` entry 已删除
- `succeededEntries` 中存在该 entry id 的凭据

只有当上述两个条件同时满足时，本地才标记 `completedCredentialAt`，下个 cycle 才能启动。

## 2. visitId 生成与切换流程

### 2.1 首次有效持久化（原子化）

```ts
async function ensureVisitId(stageId, tabId): Promise<{ visitId, sessionId }> {
  return db.transaction('rw', db.playbackVisits, db.playbackState,
                        db.runtimeOutbox, db.runtimeChainHeads, async () => {
    // 1. 查当前 stage 下所有 visit，按 completedCredentialAt 排序
    const visits = await db.playbackVisits
      .where('stageId').equals(stageId)
      .reverse().sortBy('createdAt');
    
    // 2. 若有 active visit → 复用
    const active = visits.find(v => v.status === 'active');
    if (active) return { visitId: active.visitId, sessionId: active.sessionId };
    
    // 3. 若最近 visit 已 completed → 新建 visit
    const latest = visits[0];
    if (latest?.completedCredentialAt) {
      return _createNewVisit(stageId, tabId);
    }
    
    // 4. 无任何 visit → 全新创建
    return _createNewVisit(stageId, tabId);
  });
}
```

### 2.2 append/create 时序

```ts
async function appendSnapshot(stageId, snapshot) {
  const { visitId, sessionId } = await ensureVisitId(stageId, getTabId());
  
  return db.transaction('rw', db.runtimeOutbox, db.runtimeChainHeads, async () => {
    // create 永远 active
    const createId = await _qEnqueue({
      sessionId, op: 'create_session',
      body: { id: sessionId, kind: 'playback', stageId,
              status: 'active', ... },
    });
    const appendId = await _qEnqueue({ ... }, createId);
    return { visitId, sessionId, createId, appendId };
  });
}
```

### 2.3 set_status completed 仅在已 send append 后

不在 snapshot 入队路径中直接 set_status completed（保持 R2.1 行为）。
`completed` 仅在用户播放完毕 → 已 send append → 触发 set_status。

## 3. Legacy/Outbox 迁移（v0.1 缺失）

### 3.1 已存在的 pb:<stageId> outbox 条目

**保持原 session identity**：
- 旧条目 session id = `pb:<stageId>`（不含 visitId）
- 不可重新绑定到新 visit
- 这些条目继续走原 server 路径（pb:<stageId>）

理由：
- 重绑定需查找旧 session id 是什么（数据可能丢失）
- 已 signed commit 不可改

### 3.2 哪些 409 判定为不可恢复

**当出现 409 INACTIVE_SESSION**（来自 §3.1 旧条目对 completed session 的重试）：
- 检查 `runtimeOutbox` 该 session 是否所有 set_status(completed) 已成功凭据化
- 若已成功 → 旧条目的 session 已 closed → **永久 dead**
- 若未完成 → 继续重试（race 罕见）

实现：依赖 R3.1 现有 cascadeMarkDeadInTx。状态机层面已具备条件：
- append_record(grade) 依赖的 set_status(completed) 已 succeeded → 后续所有 pending 链路 dead

### 3.3 新 visit 不依赖旧死链

新 visit 入队的所有 create/append 链路独立。
新 visit 的 session id = `pb:<stageId>:<newVisitId>`，与旧 `pb:<stageId>` 不同。

scheduler 解析新 visit 的依赖链只走 runtimeChainHeads + 新 session 的 outbox 条目，
不受旧 `pb:<stageId>` 失败条目影响。

### 3.4 终结留下原因与遥测

状态从 pending → dead 时记录原因字段：
```ts
RuntimeOutboxEntry = {
  ..., // 现有
  deadReason?: string;  // 'session_closed' | 'INACTIVE_SESSION_permanent' | ...
  deadAt?: string;
};
```

`telemetry` 上报 `runtime_shadow` event，outcome='dead' 增加 deadReason 字段。

### 3.5 死链终结的具体规则

| 场景 | 旧条目命运 |
|------|----------|
| 旧 `pb:<stageId>` create 仍在 pending | 继续重试（原行为）|
| 旧 `pb:<stageId>` set_status completed 成功凭据已落 | 旧链全部 dead（cascade）|
| 旧条目 dead 后，新 visit 不受影响 | ✅ |

## 4. E2E 门禁（v0.2 补全）

按评审要求列出 8 个场景。每场景 = 1 个 E2E 测试用例。

### 4.1 单标签页

| # | 场景 | 期望 |
|---|------|------|
| 1 | 首次进入课程，播放 3 个场景 | outbox 全部 201，最终 set_status completed 200，sessionId 含 visitId |
| 2 | 首笔快照即 completed（用户打开即拉到末页） | create(active)→append→completed 全部 201/200，无 409 |
| 3 | completed 成功后重新进入课程 | 新 visitId（与上一次不同），新 sessionId，append 201 |
| 4 | completed PATCH 失败后刷新，仍复用原 visit | 同一 visitId，retry set_status 同一 session |

| 6 | 课程中切场景（同 visit） | 同一 sessionId，append 201，仅 actionIndex 递增 |
| 7 | 旧 pb:<stageId> 失败条目不阻断新 visit | 新 visit 独立完成；旧条目 dead |

### 5.2 迁移路径

升级 v17→v18 步骤：
1. 保留旧 `playbackState` 表所有行
2. 不重建 visits 表（按需创建）
3. 旧 `runtimeOutbox` 中 `pb:<stageId>` 条目保持不动
4. 客户端首次访问时若发现 visits 表空 → 按 playbackState 中数据初始化

### 5.3 不变性

- v18 schema 与 v17 数据兼容
- 旧 session id `pb:<stageId>` 仍合法（服务端不感知）
- 新 session id `pb:<stageId>:<visitId>` 服务端不感知
- R3.2 quiz 行为不变

## 6. 与 R3.2 chain reorder 关系

| 项 | R3.2 quiz | R3.1a playback |
|----|-----------|---------------|
| 服务端约束 | append_record 在 completed 后被拒 | 同 |
| 客户端方案 | chain reorder：所有 append 在 status 翻转前 | visitId 隔离：completed 后新建 session |
| 解决路径 | 单 session 内顺序调整 | 跨 session 隔离 |
| 共用契约 | create 永远 active，append 在前，set_status 在后 | 同 |

**复用 R3.2 结论**：create 永远不能直接创建 completed session。v0.2 §1.5 即此结论在 playback 上的应用。
