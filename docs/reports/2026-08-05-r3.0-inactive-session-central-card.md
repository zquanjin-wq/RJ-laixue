# 设计卡任务书：R3.0 中央 INACTIVE_SESSION 分类

**编号**: R3.0-C1（R3.1a 实施链第一环）
**下达日期**: 2026-08-05
**下达方**: 评审/规划（Codex 角色）
**作者**: 待定（起草后交评审签字，签字后才允许实施）
**前置**: R3.1a 设计 SIGNED（`e3128448`，v0.5 + v0.5.1–v0.5.3 勘误链）
**性质**: 独立小卡——只动 R3.0 中央响应分类，不触碰 playback/quiz 业务侧

---

## 1. 目标

让 R3.0 outbox 中央响应处理正确分类 `409 INACTIVE_SESSION`：**永久 dead，不重试**，
reason 归入 R3.1a 已签的 DeadReason 体系。这是 R3.1a 实施的前置——没有它，
completed session 后的滞留 append 会继续按未知 409 退避重试直到 `max_retries`，
既浪费请求又让 dead 原因失真。

## 2. 现状（评审已核实的代码事实）

`lib/runtime/outbox.ts` 409 分支（dequeueOne 内）：

- `create_session` + `CONFLICT` → 幂等成功（succeededEntries 落凭据）；
- `IDEMPOTENCY_CONFLICT` → 递归 cascade dead，telemetry reason='idempotency_conflict'；
- 非 create 且 errorCode 为空 → 按死信（旧格式兜底）；
- **其余 409（含 INACTIVE_SESSION）→ `throw` → catch 走 attempts+1 退避重试，
  直到 DEAD_AFTER_ATTEMPTS 后以 reason='max_retries' 进 dead**。

`extractErrorCode(resp)` 为模块内私有函数（未 export），入参是 Response——
R3.1a v0.5 §3.1 已裁定：playback 外围不得自行消费 Response，一切在本卡中央处理。

## 3. 设计要求（必须覆盖）

1. **分类规则**：409 且 `errorCode === 'INACTIVE_SESSION'` → 当前 entry 永久 dead，
   并级联其依赖后继（复用 `cascadeMarkDeadInTx`），**不进入重试**；
2. **DeadReason 对齐**：deadReason 字段使用 R3.1a 已签枚举
   `INACTIVE_SESSION_permanent` / `IDEMPOTENCY_CONFLICT_permanent` / `CASCADE_DEAD`；
   现有 `idempotency_conflict`/`max_retries` 遥测 reason 与字段值的映射关系必须在
   卡内写清（字段落库、暂不上报 diagnostics 的边界沿用 R3.1a v0.5 §3.3）；
3. **create_session 的 INACTIVE_SESSION 不可能出现**（create 不依赖会话活跃），
   若出现按未知 409 重试——卡内需显式说明这一分类边界；
4. **不改变** 404 恢复链（handle404）、create CONFLICT 幂等成功、未知 409 重试
   这三条既有已签路径的行为；
5. **空 errorCode 兜底顺序**：现有「非 create 空 errorCode 按死信」与新增
   INACTIVE_SESSION 分支的判定顺序必须写明，不得产生分类歧义；
6. **lease/CAS 保护**：dead 落库必须沿用现有 `sending + leaseOwner` 匹配事务，
   过期响应不得误杀。

## 4. 门禁（设计卡必须附带、实施后用单测证明）

| # | 场景 | 期望 |
|---|------|------|
| C1-1 | append 收到 409 INACTIVE_SESSION | 当次即 dead，reason=INACTIVE_SESSION_permanent，attempts 不增，无退避重试 |
| C1-2 | 该 append 有 status 后继 | 级联 dead，reason=CASCADE_DEAD |
| C1-3 | set_status 收到 409 INACTIVE_SESSION | 同 C1-1 |
| C1-4 | create_session 收到 409 INACTIVE_SESSION（构造异常） | 按未知 409 重试，不 dead |
| C1-5 | 空 errorCode 409（非 create） | 维持旧死信兜底，分类不受新分支影响 |
| C1-6 | 409 IDEMPOTENCY_CONFLICT | 维持既有递归 dead，reason 映射符合 §3.2 |
| C1-7 | 过期 lease 的 409 INACTIVE_SESSION 响应 | 不落 dead（CAS 拒绝） |

## 5. 边界（明确不做）

- 不改 playback/quiz/chat 任何业务侧代码；
- 不实现 dead telemetry 上报 client-diagnostics（等 diagnostics 契约卡）；
- 不动 R3.1a 的 visit/cycle 逻辑（那是后续实施卡）；
- 不触碰 Production、环境变量、SQL。

## 6. 交付物与流程

1. 作者提交设计卡（含现状核对、分类判定表、伪代码、7 条门禁的可测试写法）；
2. 评审逐行核对后签字或打回；
3. 签字后负责人另行授权实施，实施完成跑门禁 + 回归（`tests/runtime*` 全量）；
4. 然后才进入 R3.1a 的 Dexie v18 / cycle identity 实施卡。
